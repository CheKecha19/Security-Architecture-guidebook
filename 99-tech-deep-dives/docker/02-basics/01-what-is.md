# Что такое Docker: контейнеризация для всех

> **Коротко:** Docker — это платформа, которая упаковывает приложение и всё, что ему нужно для работы, в изолированный «контейнер». Этот контейнер можно запустить на любом компьютере, сервере или в облаке — и он будет работать одинаково. Никаких «на моей машине всё работает», никаких ручных установок зависимостей.

---

## Проблема, которую решает Docker

Представьте: вы разрабатываете веб-приложение. В нём фронтенд на React, бэкенд на Python и база данных PostgreSQL. Чтобы всё это запустить локально, нужно:

1. Установить Node.js нужной версии
2. Установить Python нужной версии
3. Установить PostgreSQL нужной версии
4. Настроить переменные окружения
5. Настроить порты и сетевые взаимодействия
6. …и повторить всё это на машине коллеги, на тестовом сервере и в продакшене

На каждом шаге что-то может пойти не так. Версия Node.js отличается. Python конфликтует с системным. PostgreSQL занял нужный порт. Знакомая ситуация?

**Docker решает эту проблему радикально.** Вместо того чтобы устанавливать зависимости на каждой машине, вы упаковываете приложение в контейнер — изолированную среду, которая содержит всё необходимое. Контейнер запускается одинаково на любом хосте: вашем ноутбуке, сервере в дата-центре или в облаке AWS.

Это не просто удобство — это **устранение целого класса проблем.** Проблема «It works on my machine» (на моей машине работает) — профессиональная шутка разработчиков, за которой стоят миллионы потерянных часов отладки. Docker делает эту фразу историей.

### Почему эта проблема возникла

До Docker существовало несколько подходов к изоляции окружений:

- **Виртуальные окружения** (Python venv, Ruby rbenv, Node nvm) изолируют только пакеты языка, но не системные библиотеки, не базы данных, не сетевые настройки
- **Виртуальные машины** (VirtualBox, VMware) изолируют всё, но ценой гигантского оверхеда: каждая VM тащит полную копию ОС, медленно запускается и жрёт гигабайты памяти
- **Ручная настройка серверов** — «установи то, настрой это» — невоспроизводима, подвержена ошибкам и дрейфу конфигурации

Docker занял золотую середину: изоляция как у VM, лёгкость как у виртуального окружения, скорость запуска — секунды.

## Что такое контейнер — аналогии

Понимание контейнеров начинается с правильных аналогий. Вот три — от самой простой к самой точной.

### Аналогия №1: Морской контейнер

В реальном мире стандартизированный морской контейнер произвёл революцию в логистике в 1950-х годах. До контейнеров грузы были разных форм и размеров, каждый требовал особого обращения при погрузке и разгрузке. Контейнеры сделали процесс единообразным:

| Реальный мир | Мир Docker |
|---|---|
| Морской контейнер | Docker-контейнер |
| Груз (товары) | Приложение и его зависимости |
| Корабль / поезд / грузовик | Ноутбук / сервер / облако |
| Стандартные крепления и габариты | Стандартный интерфейс контейнера (`docker run`, порты, тома) |
| Портовая инфраструктура | Docker Engine |
| Крановщику всё равно, что внутри | Серверу всё равно, какое приложение внутри контейнера |

Один и тот же контейнер грузится на корабль, поезд или грузовик. Содержимое не важно — важен только стандартный интерфейс. Именно эту идею Docker привнёс в мир программного обеспечения.

### Аналогия №2: Квартира в многоквартирном доме

Контейнер похож на отдельную квартиру в многоквартирном доме:

- У каждой квартиры — **свои стены** (изоляция процессов и файловой системы)
- **Своя кухня и санузел** (зависимости и библиотеки)
- **Свой замок на двери** (изоляция безопасности)
- Жильцы одной квартиры **не мешают жильцам другой** (контейнеры изолированы)
- Все квартиры используют **общий фундамент, водопровод и электричество** (ядро ОС хоста)
- Если в одной квартире пожар — **остальные устоят** (сбой одного контейнера не рушит остальные)

Главное отличие от реального дома: Docker-«квартиру» можно мгновенно скопировать, перенести на другой сервер и запустить там — без переезда и грузчиков.

### Аналогия №3: Образ как чертёж, контейнер как здание

**Образ (Image)** — это чертёж здания. В нём описано всё: сколько этажей, где какие стены, какая проводка. Чертёж — это документ, а не здание; по одному чертежу можно построить сколько угодно одинаковых зданий.

**Контейнер** — это построенное по чертежу здание уже с мебелью и жильцами внутри. Это работающий экземпляр.

**Dockerfile** — это инструкция для архитектора: «возьми фундамент от здания А, добавь на второй этаж кухню, на третий — библиотеку, проведи электричество».

Эта аналогия точно передаёт отношение: один образ → много контейнеров. Образ неизменяем, контейнер живёт своей жизнью (пишет данные, обрабатывает запросы).

## Контейнеры vs Виртуальные машины

Это самый частый вопрос от новичков. Разница принципиальная и её важно понять с первого раза.

### Как это работает на уровне архитектуры

**Виртуальная машина** запускается через гипервизор (Hyper-V, VMware ESXi, KVM) — программу, которая эмулирует железо: процессор, память, диски, сетевые карты. На это эмулированное железо устанавливается полноценная гостевая операционная система со своим ядром, драйверами и системными службами. И только поверх всего этого запускается приложение.

**Docker-контейнер** не эмулирует железо. Он использует механизмы ядра Linux (namespaces и cgroups) для изоляции процесса. Контейнер — это группа процессов, которая «думает», что находится в отдельной ОС, но на самом деле разделяет ядро с хостом.

### Визуальное сравнение

```
=== ВИРТУАЛЬНЫЕ МАШИНЫ ===
┌───────────────────────────────────────────────┐
│  VM 1               VM 2               VM 3   │
│ ┌──────────────┐  ┌──────────────┐  ┌───────┐ │
│ │ Приложение   │  │ Приложение   │  │ Прил. │ │
│ │ Библиотеки   │  │ Библиотеки   │  │ Библ. │ │
│ │ Guest OS     │  │ Guest OS     │  │GuestOS│ │
│ │ (своё ядро)  │  │ (своё ядро)  │  │(ядро) │ │
│ └──────────────┘  └──────────────┘  └───────┘ │
│                Гипервизор                       │
│                Host OS                          │
│                Железо                           │
└───────────────────────────────────────────────┘

=== DOCKER-КОНТЕЙНЕРЫ ===
┌───────────────────────────────────────────────┐
│  Контейнер 1    Контейнер 2    Контейнер 3    │
│ ┌──────────────┐  ┌──────────────┐  ┌───────┐ │
│ │ Приложение   │  │ Приложение   │  │ Прил. │ │
│ │ Библиотеки   │  │ Библиотеки   │  │ Библ. │ │
│ └──────────────┘  └──────────────┘  └───────┘ │
│                Docker Engine                   │
│                Host OS (общее ядро Linux)      │
│                Железо                           │
└───────────────────────────────────────────────┘
```

### Сравнительная таблица

| Характеристика | Виртуальная машина (VM) | Docker-контейнер |
|---|---|---|
| **Уровень изоляции** | Аппаратный — эмуляция железа, своё ядро ОС | Процессный — namespaces, cgroups, общее ядро |
| **Размер образа** | Гигабайты (образ ОС + приложение) | Мегабайты — сотни мегабайт |
| **Время запуска** | Минуты (загрузка ОС, системных служб) | Секунды (запуск процесса) |
| **Потребление ресурсов** | Значительное — каждая VM резервирует CPU/память | Минимальное — разделяет ресурсы хоста динамически |
| **Плотность на сервере** | Единицы — десятки VM на хост | Десятки — сотни контейнеров на хост |
| **Портативность** | Привязана к гипервизору и формату образа | Запускается везде, где есть Docker Engine |
| **Производительность** | ~90-95% нативной (оверхед гипервизора) | ~98-99% нативной (оверхед минимален) |
| **Безопасность изоляции** | Высокая (отдельное ядро) | Средняя (общее ядро, компенсируется практиками) |

### Ключевой вывод

Виртуальная машина — это «компьютер внутри компьютера». Контейнер — это «процесс, который думает, что он один в операционной системе».

**На практике VM и контейнеры часто используют вместе** — и это не противоречие:

- В облаке выделяется виртуальная машина как единица изоляции между клиентами
- Внутри этой VM через Docker запускаются десятки контейнеров приложений
- Так достигается и безопасность (VM защищает клиентов друг от друга), и эффективность (контейнеры утилизируют ресурсы VM)

Это стандартный паттерн для AWS ECS, Google Cloud Run, Azure Container Instances и Kubernetes-кластеров.

## Аналогия из повседневной жизни: еда навынос

Ещё одна аналогия, которая помогает понять разницу между подходами к развёртыванию приложений:

- **Без изоляции (bare metal):** Готовите еду дома. Берёте продукты, режете, жарите — и едите. Но если нужно накормить друга в другом городе, придётся покупать продукты заново и готовить там. Результат будет другим — плита друга греет иначе, продукты из другого магазина.

- **Виртуальная машина:** Отправляете другу целую кухню в контейнере. Плита, холодильник, посуда, продукты. Друг ставит эту кухню у себя в квартире, подключает газ и электричество — готовит по вашему рецепту. Затратно, но изолировано.

- **Docker-контейнер:** Отправляете другу готовую еду в термоконтейнере. Суп уже сварен, температура поддерживается. Друг открывает крышку и ест. Быстро, дёшево, идентично тому, что у вас. Разогрев (запуск) — 30 секунд.

## Ключевые концепции Docker

В основе Docker лежат четыре связанные сущности. Их понимание — фундамент для всего остального.

### 1. Dockerfile — рецепт сборки

**Dockerfile — текстовый файл с инструкциями по созданию образа.** Это «рецепт»: что взять за основу, что добавить, как приготовить.

Минимальный Dockerfile для Python-приложения:

```dockerfile
# База — официальный образ Python (лёгкая версия)
FROM python:3.11-slim

# Рабочая директория внутри будущего контейнера
WORKDIR /app

# Копируем файл зависимостей (отдельно от кода — для кэширования)
COPY requirements.txt .

# Устанавливаем зависимости
RUN pip install --no-cache-dir -r requirements.txt

# Копируем исходный код
COPY . .

# Порт, который слушает приложение (информативно, не пробрасывает автоматически)
EXPOSE 8000

# Команда запуска при старте контейнера
CMD ["python", "app.py"]
```

**Почему COPY requirements.txt отдельно от COPY . ?** Это осознанный приём: зависимости меняются редко, код — часто. Если сначала скопировать requirements.txt и выполнить `pip install`, Docker закэширует этот слой. При следующей сборке, если requirements.txt не изменился, pip install не выполнится заново — сэкономлены секунды (или минуты для тяжёлых зависимостей).

### 2. Образ (Image) — неизменяемый шаблон

**Образ — результат выполнения Dockerfile.** Это бинарный артефакт, содержащий всё необходимое для запуска приложения: код, среду выполнения, системные библиотеки, конфигурационные файлы.

Свойства образа:
- **Неизменяем** (immutable). Созданный образ нельзя отредактировать — только пересобрать заново
- **Слоистый.** Каждая инструкция Dockerfile создаёт новый слой. Слои кэшируются и переиспользуются между образами — экономия дискового пространства и времени сборки
- **Адресуется тегом.** `python:3.11-slim`, `myapp:v1.2.3`, `nginx:latest`
- **Хранится в реестре (Registry).** Локально или удалённо — Docker Hub, AWS ECR, GitLab Container Registry, self-hosted registry

Образ — это как ISO-файл операционной системы или `.apk` для Android. Но в отличие от ISO, образ Docker не содержит ядра ОС — только userspace.

### 3. Контейнер (Container) — запущенный экземпляр образа

**Контейнер — это работающий процесс (или группа процессов), изолированный от хоста и других контейнеров.** Создаётся из образа командой `docker run`.

Свойства контейнера:
- **Эфемерен по умолчанию.** После остановки и удаления контейнера все его внутренние данные теряются (если не использованы тома — volumes)
- **Изолирован:** своя файловая система, своё сетевое пространство, своё дерево процессов
- **Один образ — много контейнеров.** Можно запустить 100 контейнеров из одного образа — все будут идентичны на старте
- **Связан с хостом явно:** порты (`-p`), тома (`-v`), переменные окружения (`-e`) — контейнер не видит ничего лишнего

### 4. Реестр (Registry) — хранилище образов

**Registry — это сервер, на котором хранятся и откуда скачиваются образы.** По умолчанию Docker работает с Docker Hub — крупнейшим публичным реестром с миллионами готовых образов.

Жизненный цикл образа в контексте реестра:
```bash
# Скачать образ из реестра
docker pull nginx:latest

# Собрать и пометить свой образ (префикс — адрес реестра)
docker build -t myregistry.example.com/myapp:v1.0 .

# Отправить образ в реестр
docker push myregistry.example.com/myapp:v1.0
```

Популярные реестры:
- **Docker Hub** — публичный реестр по умолчанию, самый большой
- **AWS Elastic Container Registry (ECR)** — закрытый реестр внутри AWS
- **GitHub Container Registry (ghcr.io)** — интегрирован с GitHub Actions и репозиториями
- **GitLab Container Registry** — встроен в GitLab, один проект = один реестр
- **Harbor** — self-hosted реестр с корпоративными фичами (сканер уязвимостей, RBAC, репликация)

### Как всё связано — полный цикл

```
Dockerfile  ──(docker build)──▶  Image  ──(docker push)──▶  Registry
                                     │
                                     │ (docker pull, docker run)
                                     ▼
                                 Container 1  Container 2  Container N
                                (работает на   (работает на   (работает в
                                 ноутбуке)     тестовом       облаке AWS)
                                               сервере)
```

Один Dockerfile → один образ → сотни идентичных контейнеров → один результат везде.

## Когда использовать Docker (и когда — нет)

Docker — мощный инструмент, но не серебряная пуля. Вот практическое руководство по принятию решения.

### ✅ Docker нужен, когда:

#### 1. Командная разработка
Все используют одинаковое окружение — версии языков, библиотек, баз данных. Новый разработчик запускает проект одной командой: `docker compose up`. Онбординг сокращается с нескольких дней до 15 минут.

#### 2. Микросервисная архитектура
Каждый сервис живёт в своём контейнере. Независимое масштабирование: сервис корзины крутится в 3 экземплярах, а сервис аналитики — в 10. Независимые обновления: обновили сервис оплаты — фронтенд и каталог не трогали. Независимые сбои: упал сервис рекомендаций — сайт продолжает принимать заказы.

#### 3. CI/CD (непрерывная интеграция и доставка)
Сборка и тестирование происходят в одинаковых контейнерах. То, что прошло тесты — гарантированно работает в продакшене. Пайплайн выглядит так:

```
git push → GitHub Actions запускает docker build → прогоняет тесты в контейнере →
docker push в реестр → деплой на сервер → docker pull && docker run → приложение обновлено
```

#### 4. Изоляция окружений на одном сервере
Десятки приложений на одном хосте без конфликтов зависимостей. Приложению А нужен Python 3.9, приложению Б — Python 3.12. С Docker это не проблема — они живут в разных контейнерах и не видят друг друга.

#### 5. Быстрое масштабирование
Контейнер запускается за секунды. При пиковой нагрузке (Чёрная пятница, релиз, DDoS) можно мгновенно развернуть дополнительные экземпляры.

#### 6. Песочница для экспериментов
Хотите попробовать MongoDB? `docker run mongo` — и через 10 секунд у вас работающая база данных. Не понравилось — `docker rm` и никаких следов в системе. Никаких танцев с установкой, настройкой и удалением.

### ❌ Docker не нужен, когда:

#### 1. Статический сайт из трёх HTML-страниц
FTP-загрузка на хостинг за 150 рублей в месяц — быстрее и проще, чем настройка Docker + reverse proxy + SSL.

#### 2. Одно приложение на одном сервере — без команды
Одиночный Python-скрипт или простое монолитное приложение прекрасно живут с виртуальным окружением (venv) и systemd. Docker здесь — избыточное усложнение.

#### 3. Жёсткие требования к производительности
Контейнеризация добавляет минимальный, но ненулевой оверхед (обычно < 3-5%). Для высоконагруженных баз данных или HPC-вычислений накладные расходы контейнеризации могут быть неприемлемы. Однако в большинстве случаев оверхед пренебрежимо мал.

#### 4. Высокие требования к безопасности изоляции (без дополнительных инструментов)
Контейнеры разделяют ядро хоста — изоляция слабее, чем у VM. Для мультиарендных систем, где в контейнерах исполняется недоверенный код, стандартного Docker недостаточно. Решения: Kata Containers (контейнер в лёгкой VM), gVisor (перехват системных вызовов), Firecracker (microVM).

#### 5. Десктопное приложение с GUI
Docker ориентирован на серверные процессы и CLI-инструменты. Запуск GUI-приложений в контейнере возможен через проброс X11-сокета, но это костыль, а не штатный сценарий.

#### 6. Вы только начинаете изучать программирование
Если вы учите Python по курсу «Hello World» — Docker добавит ненужной когнитивной нагрузки. Сначала разберитесь с языком и основными концепциями, потом возвращайтесь к Docker.

### Быстрый чек-лист для принятия решения

| Вопрос | Ответ «Да» — Docker нужен | Ответ «Нет» — можно без Docker |
|---|---|---|
| Над проектом работает > 1 человека? | ✅ Да | ❌ |
| Развёртываете приложение на нескольких серверах / в облаке? | ✅ Да | ❌ |
| Используете микросервисную архитектуру? | ✅ Да | ❌ |
| Есть CI/CD пайплайн? | ✅ Да | ❌ |
| Нужно быстро масштабироваться под нагрузкой? | ✅ Да | ❌ |
| Приложение требует специфических системных библиотек? | ✅ Да | ❌ |
| Хотите попробовать новую базу данных или технологию? | ✅ Да | ❌ |

Если 2 и более «Да» — Docker, скорее всего, оправдан.

## Экосистема Docker — что вокруг

Docker — это не один инструмент, а целая экосистема. Вот её ключевые компоненты:

### Основные инструменты Docker

| Инструмент | Назначение |
|---|---|
| **Docker Engine** | Ядро платформы. Состоит из демона (`dockerd`) — background-процесс, управляющий контейнерами, и CLI (`docker`) — интерфейс пользователя |
| **Docker CLI (`docker`)** | Командная строка. `docker build`, `docker run`, `docker ps`, `docker compose` — всё через неё |
| **Docker Compose** | Определение и запуск многоконтейнерных приложений через один YAML-файл (`compose.yaml`). Вместо 10 команд `docker run` пишете конфигурацию — и `docker compose up` поднимает всё сразу |
| **Docker Desktop** | GUI-приложение для Windows/macOS/Linux. Включает графический интерфейс, встроенный Kubernetes, управление образами и контейнерами «в окне» |
| **Docker Hub** | Публичный реестр образов. Миллионы готовых образов: базы данных, веб-серверы, языковые рантаймы, DevOps-инструменты |
| **Docker Buildx / BuildKit** | Современный движок сборки образов. Параллельное выполнение, удалённое кэширование, мультиплатформенные сборки (один образ для x86 и ARM) |
| **Docker Scout** | Анализатор безопасности образов. Сканирует зависимости на известные уязвимости (CVE), показывает рекомендации по обновлению |
| **Docker Swarm** | Встроенная оркестрация — управление кластером из нескольких Docker-хостов как единым целым |

### Внешняя экосистема (рядом с Docker)

| Инструмент | Роль |
|---|---|
| **Kubernetes (K8s)** | Де-факто стандарт оркестрации контейнеров для production. Управляет тысячами контейнеров на десятках серверов — автомасштабирование, самовосстановление, rolling updates |
| **containerd** | Низкоуровневый рантайм контейнеров. Docker использует containerd внутри себя. Стандартизирован OCI (Open Container Initiative) |
| **runc** | Самый низкий уровень — создаёт контейнер, используя механизмы ядра Linux (namespaces, cgroups). Одна задача: запустить процесс в изолированном окружении |
| **Podman** | Альтернатива Docker без демона. Совместим по командам (`alias docker=podman`). Не требует root-прав |
| **Kaniko** | Сборка образов без Docker-демона — прямо в Kubernetes-кластере. Нужна, когда нет доступа к Docker-сокету |

## Первый запуск — Docker в действии

Теория без практики мертва. Вот как выглядит путь «от нуля до работающего приложения» — три примера по нарастающей.

### Пример 1: Одноразовый веб-сервер

```bash
# Скачать образ с веб-сервером и запустить в фоне (-d)
# Порт 8080 хоста → порт 80 контейнера
docker run -d -p 8080:80 docker/welcome-to-docker

# Проверить, что контейнер запущен
docker ps
# CONTAINER ID   IMAGE                      STATUS         PORTS
# a1f7a4bb3a27   docker/welcome-to-docker   Up 5 seconds   0.0.0.0:8080->80/tcp

# Открыть http://localhost:8080 в браузере — приложение работает
```

Что произошло под капотом:
1. Docker проверил, есть ли образ `docker/welcome-to-docker` локально
2. Образа нет → скачал его из Docker Hub (послойно)
3. Создал изолированное окружение (контейнер) из образа
4. Запустил внутри веб-сервер на порту 80
5. Связал порт 80 контейнера с портом 8080 вашего компьютера

Ни одной ручной установки. Одна команда — приложение работает.

### Пример 2: База данных PostgreSQL за 10 секунд

```bash
# Запустить PostgreSQL с заданным паролем
docker run -d \
  --name my-postgres \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  postgres:16-alpine

# База данных готова к подключению
# localhost:5432, пользователь postgres, пароль secret
```

Сравните с ручной установкой PostgreSQL на Windows: найти установщик, пройти визард, указать порт, задать пароль, создать пользователя, настроить service. С Docker — одна команда, и через 10 секунд база работает. Когда она больше не нужна — `docker rm -f my-postgres` и никаких следов в системе.

### Пример 3: Полноценное приложение через Docker Compose

Файл `compose.yaml`:

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      - db
    environment:
      - DATABASE_URL=postgresql://postgres:secret@db:5432/myapp

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: myapp
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

Запуск:

```bash
docker compose up -d
# Creating network "app_default" ... done
# Creating volume "app_pgdata"   ... done
# Creating app_db_1              ... done
# Creating app_web_1             ... done
```

Одна команда — и подняты: веб-приложение, база данных, созданы сеть и том для данных. Добавьте кэш (Redis) — добавьте 6 строк в compose.yaml. Добавьте очередь (RabbitMQ) — ещё 6 строк. Архитектура описывается в конфигурации, а не настраивается вручную.

### Как удалить всё

```bash
# Остановить все контейнеры из compose.yaml и удалить их
docker compose down

# Полностью очистить: контейнеры + тома (данные БД тоже удалятся!)
docker compose down -v
```

## Распространённые заблуждения о Docker

### ❌ «Docker делает приложение быстрее»

Нет. Приложение в контейнере работает практически с нативной скоростью (оверхед < 3-5%), но не быстрее. Docker даёт изоляцию и воспроизводимость, а не магический прирост производительности.

### ❌ «Docker — это то же самое, что Kubernetes»

Нет. Docker — для запуска контейнера на одной машине. Kubernetes — для управления тысячами контейнеров на сотнях машин. Это разные уровни абстракции. Docker-контейнеры — то, *чем* управляет Kubernetes.

### ❌ «Без Docker приложение не развернуть в прод»

Нет. Можно развернуть через deb/rpm-пакеты, Git + скрипты, zip-архивы, systemd-юниты. Docker — удобный инструмент, но не единственный способ доставки кода на сервер.

### ❌ «Docker безопасен по умолчанию»

Нет. Docker помогает изолировать процессы, но это не панацея. Контейнер с уязвимостями в зависимостях уязвим в любой среде. Контейнер, запущенный с `--privileged`, имеет почти полный доступ к хосту. Безопасность требует настройки: минимальные базовые образы, сканирование уязвимостей, запуск без root-прав.

### ❌ «Docker только для Linux»

Нет. Docker Desktop работает на Windows (через WSL2 или Hyper-V) и macOS (через виртуализацию). Контейнеры на Windows/Mac запускаются в лёгкой виртуальной машине с Linux — для пользователя это прозрачно. Существуют и нативные Windows-контейнеры, но их доля рынка мала.

## Резюме

Docker превратил развёртывание приложений из «сложного и ненадёжного процесса» в «рутинную операцию из одной команды». Ключевые преимущества:

1. **Воспроизводимость** — контейнер везде работает одинаково. Эпоха «на моей машине работает» закончилась
2. **Изоляция** — приложения не мешают друг другу, даже с несовместимыми зависимостями
3. **Портативность** — из локальной разработки в облако без изменений и перенастройки
4. **Эффективность** — десятки контейнеров на одном сервере, минимальный оверхед, быстрый запуск
5. **Скорость разработки** — локальное окружение, идентичное продакшену, новые сервисы — одной командой
6. **Стандартизация деплоя** — один Dockerfile заменяет многостраничные инструкции по развёртыванию

Если вы поняли идею «упаковать приложение со всеми зависимостями в изолированный контейнер и запускать где угодно» — вы поняли Docker. Остальное — детали реализации.

Docker — не универсальное решение, но для большинства современных серверных приложений это инструмент первого выбора, на котором построена вся индустрия контейнеризации.
