# Статья #03: Ключевые архитектурные и дизайн-решения Docker

**Трек:** 01 — История и эволюция  
**Дата:** 2026-05-13  
**Статус:** Готово

---

## TL;DR

Каждая строчка кода Docker — результат осознанного выбора между простотой и гибкостью, безопасностью и удобством, монолитностью и модульностью. Docker сделал ставку на многоуровневые образы, клиент-серверную архитектуру с демоном, декларативный Dockerfile, централизованный реестр образов и собственный runtime вместо LXC. Эти пять решений определили всю индустрию контейнеризации — и породили основные точки критики, которые конкуренты (Podman, Kaniko, Buildah) используют по сей день.

## 1. Многоуровневая файловая система (Union Filesystem + Copy-on-Write)

### 1.1 Проблема: как хранить и передавать образы эффективно

Если контейнер — это изолированное окружение, то образ контейнера — это снимок файловой системы этого окружения. Прямолинейный подход: хранить полную копию всей ФС для каждого образа. Но образ с Ubuntu весит ~100+ МБ. Десяток образов — гигабайты. Передача по сети — кошмар.

**Docker выбрал слои (layers)**, и это, возможно, самое важное архитектурное решение проекта.

### 1.2 Как это работает

Каждая инструкция в Dockerfile (`RUN`, `COPY`, `ADD`) создаёт **новый слой** — дельту файловой системы относительно предыдущего состояния. Слои иммутабельны (неизменяемы) и адресуются по SHA256-хешу содержимого (content-addressable storage).

При запуске контейнера UnionFS (AUFS, OverlayFS, позже overlay2) «склеивает» все слои в единое представление файловой системы. Поверх read-only слоёв образа добавляется тонкий **writable-слой контейнера** — всё на Copy-on-Write (COW).

```
┌─────────────────────────────┐
│  Writable Layer (R/W)       │  ← контейнер
├─────────────────────────────┤
│  Layer 4: COPY app.py       │  ← read-only
├─────────────────────────────┤
│  Layer 3: RUN pip install   │
├─────────────────────────────┤
│  Layer 2: RUN apt install   │
├─────────────────────────────┤
│  Layer 1: Ubuntu base       │
└─────────────────────────────┘
```

### 1.3 Почему это гениально

| Свойство слоёв | Последствие |
|---|---|
| **Иммутабельность** | Один слой не может «испортить» другой. Образ всегда в известном состоянии |
| **Content-addressable** | Два одинаковых слоя имеют один хеш → хранятся один раз на диске |
| **Переиспользование** | 100 образов на основе `ubuntu:22.04` делят базовый слой. 100× экономия |
| **Кэширование сборки** | Если слой не изменился — пересборка мгновенная |
| **Инкрементальная передача** | `docker push/pull` передаёт только новые слои |

> **Аналогия:** Слои Docker — это как Git для файловой системы. Вместо того чтобы хранить 10 полных копий репозитория, Git хранит один базовый слепок и 10 патчей (commit'ов). Docker делает то же самое с образами.

### 1.4 Что было отвергнуто

Альтернативы:
- **Полные копии ФС** — как у VM. Огромный размер, медленная передача. Отвергнуто — противоречит идее «лёгких контейнеров».
- **Пакетный менеджер (как RPM/DEB)** — описывать зависимости пакетами. Проблема: конфликты версий в одной системе. Docker-образ — это самодостаточная единица.
- **Снапшоты ZFS/Btrfs** — хороши, но привязаны к конкретной ФС. Слои Docker работают поверх любого UnionFS-драйвера.

### 1.5 Эволюция: от AUFS до overlay2 и containerd snapshotters

- **2013–2015:** AUFS (Another UnionFS) — первый драйвер, но не в мейнлайне ядра, патч требовался
- **2015–2018:** OverlayFS пришёл в ядро Linux 3.18 → Docker перешёл на `overlay`, затем `overlay2`
- **2018+:** `overlay2` стал дефолтным драйвером — быстрее, меньше inode'ов
- **2024+:** Docker Engine 29+ использует containerd image store и snapshotters вместо legacy storage drivers

### 1.6 Обратная сторона

- **Раздувание образов:** неоптимальные Dockerfile'ы → сотни слоёв и гигабайты мусора
- **Проблема «удаления секретов»:** если `RUN` записал секрет и удалил следующим слоем — секрет всё ещё в истории слоёв
- **Оверхед COW:** интенсивная запись в writable-слой медленнее, чем прямая запись в volume

## 2. Клиент-серверная архитектура с демоном

### 2.1 Проблема: кто управляет контейнерами

Контейнеры используют возможности ядра (namespaces, cgroups), требующие привилегированного доступа. Кто-то должен эти привилегии иметь и координировать жизненный цикл контейнеров.

**Docker выбрал модель «один демон — много контейнеров».** Демон (`dockerd`) работает с правами root, слушает Unix-сокет (или TCP), принимает команды от CLI-клиента через REST API.

```
┌──────────┐  REST API   ┌──────────┐  gRPC   ┌────────────┐
│  docker  │────────────▶│ dockerd  │────────▶│ containerd │
│  (CLI)   │             │ (daemon) │         │            │
└──────────┘             └──────────┘         └────────────┘
                                                    │
                                                    ▼
                                              ┌──────────┐
                                              │  runc    │
                                              │ (OCI)    │
                                              └──────────┘
```

### 2.2 Плюсы демон-модели

- **Единая точка управления:** один процесс знает всё про все контейнеры на хосте
- **Переиспользование ресурсов:** слои образов кэшируются глобально, сеть управляется централизованно
- **REST API как универсальный интерфейс:** любой язык может управлять контейнерами через HTTP
- **Docker Compose, Swarm, оркестрация:** централизованное управление — естественный фундамент

### 2.3 Минусы (или: почему Podman существует)

- **Single Point of Failure:** упал демон — все контейнеры стали сиротами (до появления `--live-restore`)
- **Права root у демона:** пользователь с доступом к Docker-сокету = root на хосте
- **Проблема перезапуска:** обновление демона требует остановки всех контейнеров (до live-restore)
- **Форк-бомба:** демон запускает контейнеры от своего PID → все контейнеры — дети демона

Podman пошёл другим путём: **daemonless + rootless + fork-exec модель.** Каждый контейнер — независимый процесс, запущенный от пользователя без демона-посредника. Это архитектурное противостояние — центральная тема дебатов в контейнерном мире последних лет.

Docker ответил на критику: `--live-restore` (демон умер — контейнеры живут), rootless mode (экспериментально с 19.03, стабильно позже), интеграция с systemd cgroups v2.

## 3. Декларативный Dockerfile и контекст сборки

### 3.1 Проблема: как описать создание образа

До Docker создание окружения описывали shell-скриптами или конфигурационным менеджментом (Ansible, Puppet). Проблемы: недетерминизм, дрифт конфигурации, сложность воспроизведения.

**Docker выбрал Dockerfile** — простой, читаемый, декларативный DSL.

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

### 3.2 Почему это работает

- **Декларативность:** ты описываешь *что* должно быть в образе, а не *как* это сделать
- **Каждая инструкция = слой:** прямая связь Dockerfile ↔ слои → понятное кэширование
- **Воспроизводимость:** один Dockerfile → одинаковый образ на любой машине (теоретически)
- **Build context:** Docker не копирует всю машину — только указанную директорию

### 3.3 Неочевидные дизайн-решения

**Dockerfile сознательно НЕ является «скриптом» в привычном смысле** — нет циклов, условий, переменных (изначально). Это сделано для предсказуемости и кэширования.

**Build context отправляется демону целиком** перед сборкой — клиент tar'ит директорию и шлёт демону. Демон НЕ имеет доступа к файловой системе клиента. Это изолирует сборку, но создаёт проблему: `.dockerignore` обязателен, иначе `node_modules` и `.git` летят по сети.

### 3.4 Что было отвергнуто

- **Shell-скрипты вMakefile-стиле:** слишком императивно, сложно кэшировать
- **Конфигурационные файлы LXC:** слишком низкоуровнево, не для разработчиков
- **Dockerfile в самом образе:** предлагалось (#9841), но отвергнуто — образ не должен знать, как он был создан. Образ — артефакт, Dockerfile — рецепт

### 3.5 Эволюция

- **Multi-stage builds (17.05):** решение проблемы «образ для сборки vs образ для прода»
- **BuildKit (18.09+):** параллельная сборка, монтирование секретов, кэширование удалённых зависимостей
- **Docker Build Cloud (2024+):** сборка в облаке, минуя локальный контекст

## 4. Централизованный реестр образов (Registry / Docker Hub)

### 4.1 Проблема: как распространять образы

Создать контейнер локально мало. Нужен способ «взять мой образ и запустить на твоей машине».

**Docker создал Registry API и Docker Hub** — централизованный хаб для поиска, хранения и распространения образов.

```
docker pull nginx:latest
       │
       ▼
┌──────────────┐     ┌──────────────────┐
│ Docker Hub   │────▶│ Реестр (Registry)│
│ (индекс)     │     │ хранит слои      │
└──────────────┘     └──────────────────┘
```

### 4.2 Ключевые дизайн-решения

| Решение | Обоснование |
|---|---|
| **Content-addressable слои** | Позволяет дедупликацию и проверку целостности (SHA256) |
| **Registry API как HTTP REST** | Любой может написать клиент или альтернативный реестр |
| **Публичный Docker Hub** | «App Store для серверного ПО» — снижение порога входа |
| **Тэги мутабельны** | `latest` может указывать на разные образы в разное время. Спорное решение |
| **Registry v2 (2015)** | Переход с Python на Go, параллельная загрузка слоёв, content-addressable манифесты |

### 4.3 Реестр vs пакетный менеджер

Docker мог пойти по пути `apt`/`yum` — репозитории пакетов, зависимости, версионирование. Но:

- Пакетный менеджер разрешает зависимости глобально, Docker — изолированно
- Пакет оперирует файлами на уровне ОС, Docker — иммутабельными слепками ФС
- Образ — самодостаточная единица развёртывания, не требующая разрешения зависимостей

### 4.4 Что стало стандартом

Registry HTTP API V2 был передан в Open Container Initiative (OCI) в 2018 году и стал **OCI Distribution Specification** — индустриальным стандартом. Любой совместимый реестр (Docker Hub, GCR, ECR, ACR, Harbor, Quay) работает по одному протоколу.

## 5. Отказ от LXC в пользу собственного runtime (libcontainer → runc → containerd)

### 5.1 Проблема: LXC как зависимость

Первые версии Docker (0.1–0.8) использовали **LXC как execution driver.** LXC — мощный, но внешний проект со своими релизными циклами, багами и несовместимостями между дистрибутивами.

### 5.2 Решение: libcontainer (2014, Docker 0.9)

В марте 2014 Docker представил **libcontainer** — библиотеку на чистом Go, работающую напрямую с API ядра Linux (namespaces, cgroups, capabilities, AppArmor).

Цитата из анонса Docker 0.9:

> «Docker out of the box can now manipulate namespaces, control groups, capabilities, apparmor profiles, network interfaces and firewalling rules — all in a consistent and predictable way, and without depending on LXC or any other userland package.»

**Почему это важно:**
- Docker перестал зависеть от версии LXC в конкретном дистрибутиве
- Меньше moving parts → выше стабильность
- Контроль над всем стеком исполнения контейнера
- Основа для будущей стандартизации

### 5.3 Эволюция runtime

```
2013: LXC (внешняя зависимость)
  │
2014: libcontainer (свой код, прямой доступ к ядру)
  │
2015: runC (стандартный OCI runtime, подарен OCI)
  │      └── «Docker не владеет стандартом — индустрия владеет»
2016: containerd (демон управления жизненным циклом контейнеров)
  │
2017: containerd передан CNCF (Cloud Native Computing Foundation)
  │
2019: containerd graduated в CNCF
```

### 5.4 Стратегический смысл

Docker **отказался от владения ключевыми компонентами** в пользу индустриальных стандартов. Это парадоксально для бизнеса, но:
- Устранило страх vendor lock-in → ускорило adoption
- Kubernetes немедленно интегрировался с CRI-containerd
- Конкуренты (Podman, cri-o, rkt) используют те же runC и OCI-образы
- Docker сфокусировался на developer experience, а не на низкоуровневом runtime

## 6. Сводная таблица дизайн-решений

| Решение | Что выбрано | Что отвергнуто | Последствия |
|---|---|---|---|
| **Хранение образов** | Слои + UnionFS + COW | Полные копии ФС, пакетный менеджер | Экономия места, быстрое кэширование, инкрементальная передача |
| **Архитектура** | Клиент-сервер + демон | Fork-exec без демона | Простота управления, но SPOF и проблемы с правами |
| **Описание сборки** | Декларативный Dockerfile | Shell-скрипты, LXC-конфиги | Воспроизводимость, простой вход для разработчиков |
| **Распространение** | Registry + Docker Hub | Пакетные репозитории (apt/yum) | Единый каталог образов, низкий порог входа |
| **Runtime** | Свой: libcontainer → runC → containerd | LXC как внешняя зависимость | Стабильность, контроль, основа для стандартизации |
| **Стандартизация** | Передача в OCI и CNCF | Закрытый формат | Индустриальный стандарт, устранение vendor lock-in |

## 7. Ключевые дизайн-уроки

**1. Пользовательский опыт > техническая чистота.**
Docker пожертвовал архитектурной чистотой (демон с root-правами) ради UX, который поймёт любой разработчик. Это дало взрывной рост, но создало технический долг, который разгребают до сих пор.

**2. Стандартизация убивает lock-in и создаёт экосистему.**
Передав runC в OCI и containerd в CNCF, Docker потерял эксклюзивный контроль и получил всеобщий стандарт. Kubernetes, Podman, CRI-O — все работают с теми же форматами и runtime'ами.

**3. Простота входа = adoption.**
Dockerfile из 5 строк понятен новичку за 10 минут. LXC-конфиг из 100 строк — нет. Это не техническое, а продуктовое решение, и оно определило успех.

**4. Централизация создаёт эффект сети.**
Docker Hub стал «npm для контейнеров». Чем больше образов публикуется, тем ценнее платформа для всех участников.
