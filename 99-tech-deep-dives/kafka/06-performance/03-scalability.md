## TL;DR

Масштабируемость Kafka строится на трёх китах: **партиционирование** (единица параллелизма — один consumer на партицию), **горизонтальное расширение брокеров** (добавление узлов с перераспределением лидерства), и **гео-репликация** (MirrorMaker 2, stretch-кластеры, tiered storage через KIP-405). Современный KRaft-кластер (Kafka 4.0+) без ZooKeeper выдерживает **до 300 000 партиций** на кластер при времени восстановления контроллера в пределах минут. Tiered Storage (KIP-405, GA с 3.9) развязывает compute и storage — горячие данные живут на локальных NVMe (12–24 часа), холодные уходят в S3/MinIO (petabyte-scale), что снижает стоимость хранения в **3–9 раз** и ускоряет recovery после сбоя диска в **13–115 раз**. Ключевой принцип: **партиция = потолок параллелизма consumer-группы**. Нет смысла добавлять брокеров, если упёрлись в партиционный лимит.

## 1. Введение: почему масштабируемость Kafka — это архитектурный, а не инфраструктурный вопрос

Kafka с самого начала проектировалась как горизонтально-масштабируемая система. В отличие от традиционных message-брокеров (например, RabbitMQ), где масштабирование часто упирается в возможности одного узла, Kafka из коробки поддерживает распределение нагрузки по множеству серверов.

Однако «масштабируется горизонтально» — не магическое заклинание. Реальная масштабируемость определяется тремя факторами:

1. **Как данные распределены по партициям** — партиция это минимальная единица параллелизма
2. **Как кластер переживает добавление и удаление брокеров** — rebalancing, reassignment, leader election
3. **Как данные синхронизируются между дата-центрами** — geo-replication и disaster recovery

**Аналогия:** Kafka — это не одна гигантская труба, а набор параллельных труб (партиций). Ты не можешь сделать одну трубу шире — ты можешь только добавить больше труб. И количество этих труб определяет, сколько потребителей смогут одновременно «пить» из системы.

## 2. Партиционирование — фундамент масштабируемости

### 2.1 Партиция как единица параллелизма

Партиция (partition) — это основа масштабируемости Kafka. Три ключевых свойства:

| Свойство | Значение для масштабирования |
|----------|------------------------------|
| **Параллелизм consumer-ов** | Одна партиция — один consumer в группе. Больше consumer-ов, чем партиций — часть простаивает |
| **Порядок сообщений** | Гарантируется только в пределах одной партиции |
| **Распределение по брокерам** | Реплики одной партиции распределены по брокерам с учётом rack awareness |

**Главный вывод:** партиция — это одновременно и твой рычаг масштабирования, и твой потолок. Если у тебя 10 партиций на топике, максимум 10 экземпляров consumer-а могут работать параллельно. Дальше хоть 100 брокеров добавь — ускорения не будет.

### 2.2 Сколько партиций нужно: формула Goldilocks

Слишком мало партиций — bottleneck. Слишком много — операционный кошмар (metadata overhead, время перезапуска контроллера, rebalancing).

**Практическая формула:**

```
Target_Throughput = Consumer_Throughput × Partition_Count + α
```

Где:
- **Target_Throughput** — целевая пропускная способность (messages/sec)
- **Consumer_Throughput** — сколько обрабатывает один consumer-экземпляр
- **Partition_Count** — искомое количество партиций
- **α** — операционный буфер (~10–20%, покрывает rebalancing, GC-паузы)

**Пример расчёта:**
- Нагрузка: 50 000 событий/с
- Один consumer обрабатывает: 5 000 событий/с
- Минимум партиций: 50 000 / 5 000 = 10
- С буфером: 12–13 партиций

### 2.3 Практические лимиты и ограничения

| Лимит | Значение | Почему |
|-------|----------|--------|
| Партиций на брокер (ЗК) | ~4 000–6 000 | ZooKeeper начинает деградировать при 20 000+ партиций на кластер |
| Партиций на брокер (KRaft) | ~10 000+ | KRaft в 10× эффективнее ZooKeeper по метаданным |
| Максимум на кластер (KRaft) | ~300 000 | Практический предел Kafka 4.0 с KRaft |
| Минимально разумно | 3+ партиции | Меньше 3 — теряется смысл репликации и параллелизма |
| Потолок переразметки (over-partitioning) | Не более чем нужно × 1.5 | Лишние партиции только добавляют оверхед без пользы |

**Правило:** партиции можно **только добавлять** — уменьшить нельзя. Поэтому начинай консервативно. Лучше стартовать с 6–12 и добавить позже, чем создать 200 «на вырост» и страдать от metadata overhead.

### 2.4 Стратегии выбора ключа партиционирования

Распределение сообщений по партициям определяется ключом (key), по которому вычисляется хеш. Выбор ключа напрямую влияет на масштабируемость:

| Стратегия | Плюсы | Минусы | Когда использовать |
|-----------|-------|--------|-------------------|
| **Round-robin (null key)** | Идеально равномерное распределение | Никаких гарантий порядка | Логи, метрики — где порядок не важен |
| **Entity ID (user_id, order_id)** | Гарантирует порядок по сущности | Hot partition при skewed-данных | Event sourcing, CQRS |
| **Композитный ключ** (entity + timestamp) | Order + time-based windowing | Сложность key-дизайна | Stateful stream processing |
| **Кастомный partitioner** | Максимальный контроль | Код в продюсере — ещё одна точка отказа | Специфические требования к locality |

**Антипаттерн «hot partition»:** Если в качестве ключа использовать `country_code` с неравномерным распределением (скажем, 80% трафика из США), одна партиция получит 80% данных, а остальные будут простаивать. Решения:
- Разбавить ключ: `user_id + random_suffix`
- Использовать кастомный partitioner с round-robin для «горячих» ключей

## 3. Горизонтальное масштабирование брокеров

### 3.1 Добавление брокеров в кластер

Горизонтальное масштабирование — это добавление новых брокеров. Шаги:

1. **Поднять новый брокер** с уникальным `broker.id` и настроенным `broker.rack`
2. **Присоединить к кластеру** — брокер регистрируется в контроллере (ZooKeeper или KRaft)
3. **Перераспределить партиции** — через `kafka-reassign-partitions.sh`, инструменты типа Cruise Control или Strimzi Operator

**Ключевой момент:** добавление брокера само по себе не повышает производительность! Нужно вручную (или автоматически) перераспределить существующие партиции на новый брокер. Иначе он будет простаивать.

### 3.2 Перераспределение партиций (reassignment)

Это операция, которой боятся администраторы Kafka — и не зря. При reassignment данные партиции физически копируются со старого брокера на новый. Пока идёт копирование:

- Лидер остаётся на старом брокере (до завершения синхронизации)
- Продюсеры и потребители продолжают работать как обычно
- Растёт нагрузка на диск и сеть (inter-broker replication)

**Сколько времени занимает reassignment?**

```
Time = Data_Size / Replication_Speed
```

Для 5 TB данных при 100 MB/s: ~14 часов.

**Tiered Storage меняет правила игры:** Если локально хранится только 7% горячих данных (12 часов retention из 7 дней), reassignment занимает не 14 часов, а **~1 час**. Это 15× ускорение — критически важно для elastic scaling в облаке.

### 3.3 Cruise Control — автоматическое управление нагрузкой

Ручное перераспределение через JSON-файлы для `kafka-reassign-partitions.sh` не масштабируется. Cruise Control (от LinkedIn, open-source) решает эту задачу автоматически:

- **Анализирует метрики** брокеров (CPU, диск, сеть, лидерство партиций)
- **Генерирует proposal** по перераспределению
- **Выполняет reassignment** с контролируемым throttling-ом
- **Self-healing** — обнаруживает отказавшие брокеры и перераспределяет

Rack Awareness + Cruise Control = основа production-масштабирования.

### 3.4 Rack Awareness и размещение реплик

Rack Awareness (осведомлённость о стойках/зонах доступности) — ключ к отказоустойчивому масштабированию. Каждый брокер получает `broker.rack` (например, `us-east-1a`, `us-east-1b`, `us-east-1c`), и Kafka размещает реплики каждой партиции в разных rack-ах.

```
+------------------+     +------------------+     +------------------+
|   Rack: AZ-1a    |     |   Rack: AZ-1b    |     |   Rack: AZ-1c    |
| Broker 1 (L)     |     | Broker 2 (F)     |     | Broker 3 (F)     |
| Partition 0      |     | Partition 0      |     | Partition 0      |
+------------------+     +------------------+     +------------------+
          L = Leader, F = Follower
```

При отказе всей AZ-1a лидеры автоматически переходят на реплики в AZ-1b или AZ-1c — без потери данных (при `acks=all` и `min.insync.replicas=2`).

## 4. Масштабирование потребителей (Consumer Group Scaling)

### 4.1 Модель consumer-групп

Consumer-группа — механизм масштабирования потребления. Каждая партиция назначается ровно одному consumer-у внутри группы. Когда consumer-ов больше, чем партиций, лишние простаивают.

```
Topic "orders" (6 partitions)
Consumer Group "order-processor"
  Consumer-1: P0, P1
  Consumer-2: P2, P3
  Consumer-3: P4, P5
  Consumer-4: idle (нет свободных партиций)
```

### 4.2 Adaptive Scaling — динамическое масштабирование потребителей

В 2025 году тренд — адаптивное масштабирование consumer-групп на основе метрик:

- **Consumer lag > порог** (например, > 10 000) → добавить consumer-ы (scale out)
- **Consumer lag < минимум** и низкая утилизация CPU → убрать лишние (scale in)
- **Интеграция с KEDA** (Kubernetes Event-Driven Autoscaling) для автоматики

**KEDA + Kafka пример:**

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-processor-scaler
spec:
  scaleTargetRef:
    name: order-processor
  minReplicaCount: 2
  maxReplicaCount: 15
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka-brokers:9092
      consumerGroup: order-processor
      topic: orders
      lagThreshold: '10000'
```

Это позволяет consumer-ам автоматически масштабироваться от 2 до 15 реплик в зависимости от отставания.

### 4.3 Новые протоколы ребалансировки (Kafka 4.0+)

До Kafka 4.0 использовался протокол Eager Rebalancing (Stop-The-World): при добавлении/удалении consumer-а все consumer-ы группы останавливают обработку на время перераспределения партиций.

**Cooperative Rebalancing** (Incremental Cooperative Rebalancing, KIP-429) — решает эту проблему:
- Consumer-ы не останавливаются полностью
- Партиции перераспределяются инкрементально
- Consumer продолжает обрабатывать уже назначенные партиции во время ребаланса

В Kafka 4.0 Cooperative Rebalancing является рекомендуемым вариантом по умолчанию.

## 5. Гео-репликация и мульти-датацентровые архитектуры

### 5.1 Три архитектурных подхода

| Подход | RPO | RTO | Сложность | Сетевые требования |
|--------|-----|-----|-----------|-------------------|
| **Stretch Cluster** | 0 | ~секунды | Высокая | RTT < 50 мс между DC |
| **MirrorMaker 2 (async)** | Минуты | Минуты | Средняя | Умеренные |
| **Tiered Storage + S3 репликация** | Часы | Часы | Низкая | Минимальные |

### 5.2 Stretch-кластеры — нулевой RPO, но дорогие требования

Stretch-кластер — это единый логический кластер Kafka, брокеры которого физически распределены по 3 дата-центрам (для предотвращения split-brain). Каждый DC получает свою rack-метку (`dc-a`, `dc-b`, `dc-c`), и реплики каждой партиции размещаются в разных DC.

**Механика синхронной репликации:**
1. Продюсер шлёт сообщение лидеру в DC-A
2. Лидер записывает локально и рассылает фолловерам в DC-B, DC-C
3. Фолловеры подтверждают запись
4. Лидер подтверждает продюсеру

**Критические требования:**
- **3 дата-центра** (без этого невозможен кворум при отказе одного)
- **RTT < 50 мс** (иначе latency каждого write-а делает систему непригодной)
- **Выделенная полоса** между DC (пропускная способность = throughput Kafka × 2)
- **`min.insync.replicas=2`** — обязательно для защиты от потери данных

**Сценарий отказа DC:**
- При отказе DC-C контроллер удаляет брокеров DC-C из ISR-листов
- Новые лидеры выбираются из DC-A и DC-B
- Кластер продолжает работу в деградированном режиме
- **Нет потери данных** для сообщений, уже подтверждённых продюсеру

**Когда оправдано:** финансовые системы, платёжные шлюзы, core banking — где стоимость простоя превышает стоимость трёх-DC инфраструктуры.

### 5.3 MirrorMaker 2 — асинхронная гео-репликация (прагматичный выбор)

MirrorMaker 2 (MM2, KIP-382) — встроенный в Kafka инструмент на базе Connect Framework для репликации топиков между независимыми кластерами.

**Ключевые возможности MM2:**
- **Однонаправленная и bidirectional репликация** (active-active)
- **Автоматическое предотвращение циклов** (cycle detection) — сообщение не реплицируется обратно в исходный кластер
- **Сохранение смещений (offset translation)** — consumer может переключиться на зеркальный кластер без перемотки
- **Topic renaming** — топики в целевом кластере получают префикс исходного (например `us-west.orders`)

**Архитектура Active-Active через MM2:**

```
         +-----------+                    +-----------+
         |  Kafka DC |    MirrorMaker 2   |  Kafka DC |
         |    US     |<==================>|    EU     |
         +-----------+   bidirectional    +-----------+
              ↑                                 ↑
         producers                        producers
         consumers                        consumers
```

**Компромисс:** RPO измеряется минутами (зависит от replication lag), но зато:
- Нет жёстких требований к RTT (работает через интернет)
- Можно использовать 2 DC (вместо 3 для stretch)
- Каждый кластер независим в эксплуатации (можно обновлять по отдельности)

## 6. Tiered Storage (KIP-405) — революция в масштабировании хранения

### 6.1 Проблема монолитного хранения

В классической архитектуре Kafka хранит все данные на локальных дисках брокеров. Это создаёт три проблемы:

1. **Стоимость:** SSD дороги. Хранение месяцев данных на SSD — неоправданно дорого
2. **Масштабирование storage отдельно от compute:** Чтобы увеличить retention, нужно добавлять брокеры с дисками — даже если CPU не нужны
3. **Recovery time:** При отказе диска нужно перекачать все данные заново. 10 TB на 100 MB/s = больше суток

### 6.2 Как работает Tiered Storage

KIP-405 разделяет хранение на два уровня (tiers):

```
+----------------------------------+
|       HOT TIER (локальный)       |
|  NVMe SSD на брокере             |
|  Последние 12–24 часа данных     |
|  Мгновенный доступ                |
+----------------------------------+
            | offload
            v
+----------------------------------+
|      COLD TIER (удалённый)       |
|  S3 / MinIO / GCS / Azure Blob   |
|  Petabyte-scale, $0.02/GB/month  |
|  Чтение с задержкой 10–100 мс    |
+----------------------------------+
```

**Путь данных:**
1. Сообщения поступают в локальный сегмент (hot tier)
2. Когда сегмент закрывается (по времени или размеру), он offload-ится в S3
3. Consumer-ы читают из hot tier (мгновенно) или cold tier (с задержкой на первый fetch)
4. Удаление данных: локальные сегменты удаляются быстро, remote — по retention policy

### 6.3 Конкретные цифры эффективности

По данным Aiven (2024), тестирование KIP-405 на production-нагрузках показало:

| Метрика | Без Tiered Storage | С Tiered Storage | Ускорение |
|---------|-------------------|-----------------|-----------|
| Восстановление брокера после отказа диска | 230 минут | 2 минуты | **115×** |
| Produce latency при восстановлении | 290 мс | 23 мс | **12.6×** |
| Время reassignment партиции (14 дней retention) | 3 часа | 12 минут | **15×** |
| Стоимость хранения | Disk-only | S3-hybrid | **3–9× дешевле** |

### 6.4 Tiered Storage + Apache Iceberg — будущее уже здесь

Aiven разработала открытый Remote Storage Manager (RSM), который пишет данные Kafka напрямую в Apache Iceberg-таблицы в S3. Это означает:

- **Без коннекторов** — данные сразу доступны в формате Iceberg для Spark, Trino, Flink
- **Единая копия данных** — не нужно плодить копии Kafka → S3 → Data Lake
- **Catalog-agnostic** — работает с AWS Glue, Hive Metastore, Nessie

Архитектура будущего: Kafka как ingestion layer + Iceberg как long-term storage + Trino/Spark как аналитический слой. Без дублирования данных.

## 7. KRaft и масштабируемость метаданных (Kafka 4.0+)

### 7.1 Почему ZooKeeper был узким горлышком

ZooKeeper хранил все метаданные кластера: список топиков, партиций, брокеров, ISR-листы, конфигурации. При масштабировании кластера за пределы ~20 000 партиций ZooKeeper становился bottleneck-ом:

- Запись метаданных — synchronous, один leader
- Re-election ZK-лидера — десятки секунд простоя контроллера
- Split-brain scenarios при сетевых проблемах

### 7.2 KRaft: metadata-scale на порядок выше

KRaft (Kafka Raft) — это встроенный консенсус-протокол, заменивший ZooKeeper в Kafka 4.0. Ключевые улучшения для масштабируемости:

| Аспект | ZooKeeper | KRaft (Kafka 4.0) |
|--------|-----------|-------------------|
| Максимум партиций на кластер | ~20 000 | ~300 000+ |
| Время выбора контроллера | 30–60 секунд | ~1–2 секунды |
| Запись метаданных | Через ZK (отдельная система) | Внутри Kafka (единая кодовая база) |
| Dynamic quorum resize | Нет | Да (KIP-853) |
| Metadata snapshot | Нет | Да (ускоренный перезапуск контроллера) |

**Dynamic Quorum (KIP-853):** Позволяет добавлять и удалять контроллеры KRaft без остановки кластера — критически важно для масштабирования consensus layer.

### 7.3 Режимы KRaft: Combined vs Isolated

| Режим | Описание | Когда использовать |
|-------|----------|-------------------|
| **Combined** | Брокер и контроллер в одном процессе | Кластеры до 30 брокеров, dev/staging |
| **Isolated** | Отдельные узлы для контроллеров | Production > 30 брокеров, требования к стабильности |

Isolated mode предотвращает ситуацию, когда нагрузка на брокер (CPU, GC) мешает работе контроллера — критично для крупных кластеров.

## 8. Стратегия масштабирования: пошаговый план

### 8.1 Последовательность действий при росте нагрузки

```
1. МОНИТОРИНГ → обнаружь bottleneck
2. ОПТИМИЗАЦИЯ → исключи конфигурационные ошибки
3. ПАРТИЦИИ → добавь, если consumer-ы упёрлись
4. CONSUMER-Ы → добавь экземпляров (до partition count)
5. БРОКЕРЫ → добавь, если диски/CPU на пределе
6. ГЕО → реплицируй между DC, если нужно DR
7. TIERED STORAGE → включи, если retention > 7 дней или диски дороги
```

### 8.2 Чеклист production-масштабирования

- [ ] Партиций достаточно для peak consumer parallelism + 20% буфера
- [ ] Ключ партиционирования выбран осмысленно (нет hot partition)
- [ ] Rack Awareness настроен (broker.rack)
- [ ] `min.insync.replicas=2` (для RF=3) или `3` (для RF=5)
- [ ] Cooperative Rebalancing включён на consumer-ах (partition.assignment.strategy)
- [ ] Cruise Control или аналог для автоматического reassignment
- [ ] MM2 или stretch-кластер для меж-DC репликации (если нужно)
- [ ] KRaft Isolated Mode для кластеров > 30 брокеров
- [ ] Tiered Storage для retention > 7 дней или кластеров > 50 TB
- [ ] Метрики: UnderReplicatedPartitions, IsrShrinksPerSec, Consumer Lag, Controller Active Count

## 9. Реальные примеры масштабирования

### 9.1 LinkedIn — родина Kafka

LinkedIn оперирует сотнями кластеров Kafka, обрабатывающих **триллионы сообщений в день**. Ключевые цифры:

- Миллионы партиций суммарно
- Cruise Control для автоматического перераспределения

### 9.2 Uber — 150 GB/s через Tiered Storage

Uber одним из первых внедрил Tiered Storage (KIP-405) на нагрузках **>150 GB/s**. Это позволило:

- Ускорить recovery broker-а с часов до минут
- Упростить capacity planning (S3 растёт автоматически)

### 9.3 Apple и Datadog — тестирование KIP-405

Apple и Datadog участвовали в тестировании open-source плагина Tiered Storage для AWS S3 (Aiven), подтвердив его пригодность для petabyte-scale нагрузок.

## 10. Типичные ошибки при масштабировании

| Ошибка | Симптомы | Решение |
|--------|----------|---------|
| Слишком много партиций «на вырост» | Долгий перезапуск контроллера, memory pressure | Начать с 6–12, добавлять по мере роста |
| Нет Rack Awareness | Все реплики в одной AZ → потеря данных при отказе AZ | Настроить broker.rack, пересоздать топики |
| Consumer-ов больше, чем партиций | Лишние consumer-ы idle, деньги на ветер | Partition count ≥ max consumer count |
| `min.insync.replicas=1` | Потеря данных при отказе лидера до репликации | `min.insync.replicas=2` минимум |
| Масштабирование consumer-ов без Cooperative Rebalancing | Stop-the-world при любом scale-событии | Включить Cooperative Rebalancing |
| Игнорирование Tiered Storage | Дорогие SSD, медленный recovery | Включить для retention > 1 недели |

## Заключение

Масштабируемость Kafka — это не одна настройка, а система архитектурных решений:

- **Партиционирование** задаёт потолок параллелизма — считай по формуле, начинай консервативно
- **KRaft (Kafka 4.0)** убирает ZooKeeper как узкое горлышко — 300K+ партиций на кластер реально
- **Tiered Storage (KIP-405)** разделяет compute и storage — 3–9× дешевле, 115× быстрее recovery
- **MirrorMaker 2** для прагматичной гео-репликации, Stretch-кластеры для нулевого RPO (но с большими требованиями к сети)
- **Cruise Control + KEDA** для автоматического перераспределения нагрузки и adaptive scaling consumer-ов

Главный принцип: **масштабируй по метрикам, а не по интуиции.** UnderReplicatedPartitions > 0, IsrShrinksPerSec spikes, Consumer Lag растущий — вот реальные сигналы к действию, а не абстрактное «нагрузка выросла».
