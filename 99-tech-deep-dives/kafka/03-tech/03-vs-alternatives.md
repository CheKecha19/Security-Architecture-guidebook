# Kafka vs Альтернативы: Сравнительный Анализ

**Нижняя строка:** Kafka — не единственный инструмент на рынке событийного стриминга. Выбор между ним и альтернативами сводится к трём осям: архитектурный подход (лог против очереди), операционная сложность (JVM против single binary) и зрелость экосистемы. Каждый конкурент силён в своём сценарии — универсального победителя нет.

---

## Карта Конкурентов: Три Категории

Альтернативы Kafka группируются логикой, а не маркетингом:

| Категория | Представители | Когда рассматривать |
|-----------|--------------|-------------------|
| **Tier 1: Традиционные брокеры** | RabbitMQ, ActiveMQ, Amazon SQS | Task queues, RPC, low-latency delivery |
| **Tier 2: Стриминг-платформы** | Apache Pulsar, Redpanda, WarpStream, AutoMQ | Kafka-совместимость, cloud-native, tiered storage |
| **Tier 3: Лёгкие месседжинг-системы** | NATS, ZeroMQ, Redis Pub/Sub | Микросервисы, edge, минимальный footprint |

**Нативное программирование** (direct HTTP/gRPC между сервисами) — это нулевая точка отсчёта, не конкурент в строгом смысле. Его мы рассматриваем как «альтернативу без посредника».

## Tier 1: Традиционные Очереди Сообщений

### Kafka vs RabbitMQ — Битва Идеологий

Это самое частое сравнение, и оно же — самое неправильное, если подходить к нему как к «кто лучше». RabbitMQ и Kafka решают **разные задачи разными архитектурами**.

**Архитектурная пропасть:**

| Характеристика | Kafka | RabbitMQ |
|---------------|-------|----------|
| Модель данных | Распределённый commit log, append-only | Очереди с удалением после ACK |
| Модель доставки | Pull (потребитель тянет) | Push (брокер толкает) |
| Маршрутизация | Только topic; логика в клиентах | Exchanges (direct, topic, fanout, headers), routing keys |
| Единица параллелизма | Партиция (partition) | Очередь (queue) |
| Сохранение сообщений | Конфигурируемое (часы/дни/вечно) | До подтверждения (ACK), затем удаление |
| Повторное чтение (replay) | Нативное, смещением offset | Только Streams; классические очереди — нет |
| Гарантии порядка | Строгие в пределах партиции | В пределах очереди, зависит от consumer'а |

**Производительность (2026, эквивалентное железо c7i.4xlarge):**

| Метрика | Kafka 4.1 | RabbitMQ 4.1 |
|---------|-----------|-------------|
| Пиковая пропускная способность | ~1 000 000 msg/s на брокер | ~50 000 msg/s (classic queues); ~1M (Streams) |
| Типичная задержка (p50) | 5–15 мс | <1 мс (in-memory); 2–5 мс (persistent) |
| CPU usage | ~20% | ~40% |
| Потребление памяти | Page-cache OS, не JVM heap | Erlang VM, GC-давление на высоких объёмах |

**Почему Kafka быстрее на throughput:**
- **Пакетная запись (batching):** сообщения группируются до отправки на диск
- **Последовательный ввод-вывод:** append-only лог — самый быстрый паттерн дисковой записи
- **Zero-copy:** системный вызов `sendfile()` при чтении, данные не копируются в userspace
- **Сжатие батчей:** snappy/lz4/gzip до записи на диск
- **Page cache OS:** Kafka полагается на кэш операционной системы, а не управляет памятью в JVM

**Почему RabbitMQ выигрывает на latency:**
- Push-модель доставки: брокер отправляет сообщение немедленно, потребитель не опрашивает
- In-memory очереди: нет дискового ввода-вывода для быстрых сообщений
- Erlang/OTP: сверхлёгкие процессы, микросекундное переключение контекста

**Когда что выбирать:**

| Сценарий | Инструмент | Причина |
|---------|-----------|---------|
| Event sourcing, event-driven микросервисы | **Kafka** | Replay, retention, ordering, scale |
| Аналитические пайплайны (ClickHouse, Hadoop, Spark) | **Kafka** | Высокий throughput, партицирование |
| RPC, request-response, синхронные вызовы | **RabbitMQ** | Низкая latency, reply-to |
| Фоновые задачи, очереди заданий (email, генерация PDF) | **RabbitMQ** | Work queues, priority, dead-letter |
| IoT ingestion с миллионами устройств | **Kafka** | Горизонтальное масштабирование партиций |
| Финансовый трейдинг (низкая задержка критична) | **RabbitMQ** | Sub-millisecond p50 |
| Миграция с монолита: постепенное вынесение сервисов | **RabbitMQ** → позже Kafka | Проще начать, routing помогает декомпозиции |

**Гибридный паттерн:** Многие компании (Netflix, WeWork, Zalando) используют **оба**. RabbitMQ — для синхронных операций и фоновых задач, Kafka — для событийного стриминга и аналитики. Брокеры не заменяют, а дополняют друг друга.

**Что изменилось к 2026:**

- **Kafka 4.0 (март 2025):** ZooKeeper окончательно удалён, KRaft — единственный режим
- **RabbitMQ 4.0 (сентябрь 2024):** Mnesia заменена на Khepri (Raft-based), кластерные операции стали надёжнее
- **Kafka Queues (KIP-932):** Early access в 4.0 — per-message acknowledgement для Kafka, сближение с традиционными очередями
- **RabbitMQ Streams:** Достигают Kafka-класса throughput (~1M msg/s), добавляя replay и retention в RabbitMQ-мир

### Kafka vs ActiveMQ

ActiveMQ (Classic и Artemis) — это JMS-брокер, уходящий корнями в Jakarta EE.

| Характеристика | Kafka | ActiveMQ |
|---------------|-------|----------|
| Протокол | Binary TCP | JMS, AMQP, MQTT, STOMP, OpenWire |
| Модель | Commit log | Очереди + топики |
| Пропускная способность | ~1 000 000 msg/s | ~10 000–50 000 msg/s |
| Retention | Конфигурируемый | До ACK |
| Replay | Нативный | Нет (без внешнего хранилища) |
| Стандарт JMS | Нет (требуется адаптер) | Полная поддержка |

**Когда выбрать ActiveMQ:**
- Legacy Java-приложения, жёстко завязанные на JMS API
- Небольшие и средние нагрузки, где не нужен стриминг
- Требуется поддержка множества протоколов из коробки

**Когда переходить с ActiveMQ на Kafka:**
- Нагрузка перевалила за ~20 000 msg/s
- Появилась потребность в replay событий (event sourcing)
- Нужна интеграция с аналитическими системами (Spark, Flink, ClickHouse)

**Вывод по Tier 1:** Традиционные очереди закрывают паттерн «отправил → обработал → забыл». Kafka закрывает паттерн «сохранил поток → прочитал когда угодно → проанализировал». Это не конкуренция, а разделение труда.

## Tier 2: Стриминг-Платформы (Прямые Конкуренты)

### Kafka vs Apache Pulsar

Pulsar — единственная платформа, сопоставимая с Kafka по функциональности, но с принципиально иной архитектурой: **разделение compute (brokers) и storage (BookKeeper).**

**Архитектурное различие:**

```
Kafka: Брокер = Compute + Storage (в одном процессе)
Pulsar: Брокер (Compute) ═══ BookKeeper Bookies (Storage) — разделены
```

| Характеристика | Kafka | Pulsar |
|---------------|-------|--------|
| Архитектура | Монолитная: брокер ≡ хранение + доставка | Двухуровневая: brokers + BookKeeper |
| Масштабирование | Требует ребалансировки партиций при добавлении узлов | Мгновенное: broker загружает сегменты из BookKeeper |
| Multitenancy | Ограниченная (через квоты, ACL) | Нативная: tenant → namespace → topic |
| Tiered storage | Через плагины (Tiered Storage в Kafka) | Нативный, offload в S3/GCS |
| Geo-replication | MirrorMaker 2 | Нативная на уровне namespace |
| Подписки | Только exclusive (consumer group) | Exclusive, shared (очередь), failover, key_shared |
| Message ACK | Offset-based (последовательный) | Per-message (индивидуальный) |
| Операционная сложность | 1 компонент (KRaft) | 3–4 компонента (brokers, bookies, ZooKeeper/ metadata, RocksDB) |
| Зрелость | 14+ лет, >12% разработчиков | 8+ лет, растущая (Tencent, Discord, Flipkart) |
| Throughput | Выше в чистом стриминге (до 2×) | Сопоставим при правильной настройке |

**Когда выбрать Pulsar вместо Kafka:**
- Нужна нативная мультитенантность (SaaS-платформа, много изолированных команд)
- Требуется geo-replication без внешнего инструмента (MirrorMaker)
- Важно независимое масштабирование хранения и compute
- Нужны одновременно и очереди, и стриминг в одной системе
- Миллионы топиков (Pulsar эффективнее за счёт сегментов BookKeeper)

**Когда остаться на Kafka:**
- Максимальный throughput — главный приоритет
- Экосистема критична: Kafka Connect, Streams, Schema Registry, ksqlDB
- Команда уже знает Kafka, миграция дорога
- Нужна простота: один тип узлов (KRaft-кластер из N узлов — и всё)

### Kafka vs Redpanda

Redpanda — drop-in замена Kafka с **API-совместимостью**, написанная на C++ (без JVM, без ZooKeeper).

| Характеристика | Kafka | Redpanda |
|---------------|-------|----------|
| Язык/рантайм | Java/Scala, JVM | C++, single binary |
| ZooKeeper | Удалён в 4.0 (KRaft) | Нет (встроенный Raft) |
| Потребление памяти | JVM heap + page cache | Предсказуемое, без GC |
| Задержка p99 | Базовая | До 10× ниже при равной нагрузке |
| Schema Registry | Отдельный сервис | Встроенный |
| HTTP Proxy | Отдельный (REST Proxy) | Встроенный |
| Совместимость API | — | Полная с Kafka API (любой Kafka-клиент работает) |
| Экосистема | Kafka Streams, Connect, ksqlDB | Kafka Connect — через API совместимость; Streams — нет |

**Когда выбрать Redpanda:**
- Хочется Kafka-функциональность без операционной боли JVM (GC-паузы, тюнинг heap)
- Критична низкая и предсказуемая задержка (финтех, gaming)
- Нужен быстрый старт (один бинарник — `rpk container start` — и кластер готов)
- Встроенные Schema Registry и HTTP Proxy исключают дополнительные сервисы

**Когда остаться на Kafka:**
- Нужен Kafka Streams или ksqlDB (несовместимы)
- Экосистема Kafka Connect со 120+ коннекторами
- Enterprise-поддержка Confluent (SLA, managed cloud)
- Организация требует максимально зрелого и проверенного решения

### Kafka vs WarpStream / AutoMQ (Cloud-Native Next-Gen)

**WarpStream** — Kafka-совместимый стриминг без брокеров. Данные пишутся напрямую в S3. Ноль управляемых серверов.

**AutoMQ** — Kafka-дистрибутив, использующий S3/EBS как персистентное хранилище вместо локальных дисков брокеров.

Общее преимущество: разделение compute (stateless брокеры, автомасштабирование) и storage (object store).

**Когда рассматривать:**
- Cloud-native с нуля, 100% AWS/GCP/Azure
- Данные уже в S3 — не нужно управлять дисками
- Autoscaling нагрузки critical (burst-паттерны)

**Когда остаться на vanilla Kafka:**
- On-premises/гибридное развёртывание
- Требуется минимальная сетевая задержка (локальные диски)
- Команда не готова к vendor-specific решениям

## Tier 3: Лёгкие Месседжинг-Системы

### Kafka vs NATS

NATS — лёгкая (10 МБ бинарник Go) система, заточенная под микросервисную коммуникацию.

| Характеристика | Kafka | NATS |
|---------------|-------|------|
| Размер бинарника | ~100 МБ (JVM) | ~10 МБ (Go) |
| Модель | Commit log, pull | Pub/sub, push, request-reply |
| Persistence | Всегда на диске | JetStream (опционально) |
| Пропускная способность | ~1M msg/s | ~2–3M msg/s (core pub/sub); ниже с JetStream |
| Retention | Конфигурируемый | Через JetStream: лимит по времени/размеру/сообщениям |
| Replay | Нативный | Через JetStream consumer |
| Routing | Только topic | Subject-based, wildcards (`orders.*`, `orders.>`), queue groups |
| Протокол | Binary TCP | Текстовый NATS-протокол |
| Сложность | High | Low |

**Когда выбрать NATS:**
- Микросервисы: service discovery, pub/sub, request-reply
- Edge/IoT с ограниченными ресурсами
- Нужна минимальная задержка и накладные расходы
- Polyglot-окружение (клиенты на 40+ языках)
- Cloud-native, Kubernetes-native (NATS + K8s — естественная пара)

**Когда выбрать Kafka вместо NATS:**
- Аналитические пайплайны и ETL
- Длительное хранение событий (retention дни/недели)
- Стриминг-обработка: Kafka Streams, ksqlDB, Flink
- Уже есть Kafka Connect для интеграций

## Kafka vs Нативное Программирование (Без Посредника)

Это не конкурент в традиционном понимании, а **архитектурная альтернатива**. Вместо того чтобы слать события через брокер, сервисы общаются напрямую (HTTP/gRPC).

**Аналогия:** Kafka — это городская почта (отправил — лежит — получатель забрал когда готов). Прямой HTTP — это звонок по телефону (дозвонился — поговорил — положил трубку).

| Характеристика | Kafka | Direct HTTP/gRPC |
|---------------|-------|-----------------|
| Связность (coupling) | Низкая: producer не знает consumer | Высокая: сервис знает адрес другого сервиса |
| Надёжность доставки | Гарантии: at-least-once, exactly-once | Зависит от реализации retry + circuit breaker |
| Replay событий | Встроенный | Невозможен без собственного event store |
| Backpressure | Естественный (consumer сам решает когда читать) | Нужен circuit breaker, bulkhead |
| Observability | Единая точка мониторинга событий | Trace (distributed tracing) между парами сервисов |
| Задержка | 5–50 мс | <5 мс |
| Простота на старте | Сложнее (поднять + настроить кластер) | Проще (HTTP-библиотека) |
| Когда сервисов >5 | Экспоненциально выгоднее (M×N → M+N связей) | Экспоненциально сложнее (M×N прямых связей) |

**Правило выбора:** до 3–5 сервисов — прямой HTTP/gRPC проще. После 5 — Kafka начинает окупаться снижением связности. После 20 — Kafka практически безальтернативен.

## Сводная Матрица Выбора

| Если вам нужно… | Берите |
|-----------------|--------|
| Event sourcing, CQRS, аналитика на потоках | **Kafka** |
| Фоновые задачи, email, генерация отчётов | **RabbitMQ** |
| RPC, request-reply, низкая latency | **RabbitMQ** или **NATS** |
| Kafka без JVM и ZooKeeper | **Redpanda** |
| Multitenancy, geo-replication, S3-tiering | **Pulsar** |
| Лёгкие микросервисы, edge | **NATS** |
| Legacy Java/JMS, госкомпании, Jakarta EE | **ActiveMQ** |
| 100% AWS, serverless, zero-ops стриминг | **WarpStream** / **AutoMQ** |
| Меньше 5 сервисов, простота превыше | **Direct HTTP/gRPC** (Kafka не нужен) |

## Миграционные Стратегии

### С RabbitMQ/ActiveMQ на Kafka

1. **Не выключайте старый брокер сразу.** Запустите dual-write: сервис пишет и в RabbitMQ, и в Kafka
2. **Начните с новых потребителей** на Kafka, старые продолжают читать RabbitMQ
3. **После полного перехода потребителей** — отключите producer'ы RabbitMQ
4. **Держите rollback-план 1–2 недели** — можно быстро вернуть producer'ы обратно

### С Kafka на Pulsar/Redpanda

- **Redpanda:** Полная API-совместимость. Измените bootstrap-серверы на Redpanda — Kafka-клиенты заработают без изменений кода
- **Pulsar:** Требуется адаптация клиентов (Pulsar-клиент или Kafka-on-Pulsar handler). Проще мигрировать новые сервисы, а к старым подключать Kafka-адаптер Pulsar

### С Прямого HTTP на Kafka

- **Начните с одного потока событий:** например, «заказ создан» → Kafka topic. Остальные сервисы по-прежнему HTTP
- **Добавляйте топики постепенно:** не переводите всё сразу
- **Event schema — с первого дня:** Schema Registry (Avro/Protobuf) предотвратит breaking changes
