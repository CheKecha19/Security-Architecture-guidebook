# Как работает Apache Kafka: архитектура и внутреннее устройство

> **Нижняя строка:** Kafka работает как распределённый append-only лог, разделённый на партиции, реплицированный между брокерами и обслуживаемый через модель «умный клиент — глупый брокер». Producers пишут в лидер-партиции, брокеры реплицируют данные на follower-партиции, consumers читают с диска напрямую через page cache с zero-copy оптимизацией. Ключ к скорости — последовательный I/O, групповая отправка (batching) и отказ от копирования данных между user space и kernel space.

---

## 1. Общая архитектура: компоненты и их роли

Kafka состоит из четырёх логических слоёв:

1. **Слой хранения (Storage Layer)** — партиции на диске брокеров
2. **Слой репликации (Replication Layer)** — leader/follower модель с ISR
3. **Слой управления (Control Plane)** — KRaft quorum (до версии 4.0 — ZooKeeper)
4. **Слой вычислений (Compute Layer)** — producers, consumers, Kafka Streams, Kafka Connect

### Компонентная схема

```
                    ┌──────────────┐
                    │   KRaft      │  ← консенсус для метаданных
                    │  Quorum      │     (3-5 контроллеров)
                    └──────┬───────┘
                           │ метаданные (Fetch)
    ┌──────────────────────┼──────────────────────┐
    │                      │                      │
┌───▼────┐           ┌────▼────┐           ┌─────▼───┐
│Broker 1│◄─────────►│Broker 2 │◄─────────►│Broker 3 │  ← кластер брокеров
│part. 0 │ репликация│part. 0  │           │part. 0  │     (data plane)
│part. 1 │           │part. 1  │           │part. 2  │
│part. 2 │           │part. 2  │           │part. 1  │
└───▲──┬─┘           └────▲────┘           └───▲──┬──┘
    │  │                  │                    │  │
    │  │    ProduceRequest │    FetchRequest    │  │
    │  │                  │                    │  │
┌───┴──▼─┐         ┌──────┴──────┐      ┌─────┴──▼─┐
│Producer│         │  Consumer   │      │ Consumer │
│ Client │         │  Group A    │      │ Group B  │
└────────┘         └─────────────┘      └──────────┘
```

**Ключевое правило разделения обязанностей:** брокеры отвечают за хранение и репликацию данных. Вся логика маршрутизации, партиционирования, отслеживания offset-ов и обработки данных лежит на клиентах (producers и consumers). Это называют моделью «dumb broker — smart consumer» (глупый брокер — умный потребитель).

## 2. Storage Layer: как Kafka хранит данные

### 2.1 Topic, Partition, Segment — три уровня абстракции

```
Topic "orders" (логическая сущность)
├── Partition 0 (физический лог, один лидер на кластер)
│   ├── Segment 0 (00000000000000000000.log|.index|.timeindex)
│   │   └── messages offset 0..499
│   ├── Segment 1 (00000000000000000500.log|.index|.timeindex)
│   │   └── messages offset 500..999
│   └── Segment 2 (активный, пишется сейчас)
├── Partition 1
│   └── ...
└── Partition 2
    └── ...
```

- **Topic** — логическая категория, в которую пишут producers и из которой читают consumers. Это просто имя, а не физический файл.
- **Partition** — основная единица хранения и параллелизма. Каждая партиция — это независимый append-only лог на диске.
- **Segment** — физический файл (или группа файлов), на которые разбивается партиция для эффективного управления. По умолчанию сегмент достигает 1 ГБ, после чего Kafka «перекатывается» (roll) на новый сегмент.

Почему сегменты, а не один гигантский файл? Несколько причин:
- **Удаление:** старые сегменты можно удалить целиком, не трогая активные — это O(1), а не O(n).
- **Поиск:** найти нужный сегмент по offset можно бинарным поиском по именам файлов (они содержат base offset).
- **Восстановление:** при сбое повреждается только последний сегмент, а не вся партиция.

### 2.2 Append-only log: основа производительности

Kafka никогда не изменяет и не удаляет отдельные записи. Все операции — только append (дозапись) в конец файла:

```
Offset:  0    1    2    3    4    5    6    7    8
       ┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
       │ e1 │ e2 │ e3 │ e4 │ e5 │ e6 │ e7 │ e8 │ e9 │  ← только append →
       └────┴────┴────┴────┴────┴────┴────┴────┴────┘
         ↑                                        ↑
    oldest (удаляется                  newest (пишется сейчас)
    по retention)
```

**Почему это быстро:**

Последовательная запись на диск (sequential write) на порядки быстрее случайной (random write). Современный HDD выдаёт ~100 МБ/с на sequential write и ~100 операций/с (IOPS) на random write. SSD — ~500 МБ/с sequential против ~10 000 IOPS. Kafka эксплуатирует именно sequential I/O:

- Новые сообщения всегда дописываются в конец активного сегмента.
- Дисковый контроллер и ОС оптимизируют sequential patterns агрессивным кэшированием и prefetch-ом.
- Нет операций «найти свободное место», «обновить существующую запись», «перестроить индекс».

Результат: один брокер может записывать сотни тысяч сообщений в секунду на обычном «железе», потребляя минимум CPU.

### 2.3 Offset: уникальный адрес каждого сообщения

Каждое сообщение в партиции получает монотонно возрастающий 64-битный идентификатор — **offset**. Offset никогда не переиспользуется. Даже если сообщение удалено retention-политикой, его offset навсегда занят.

```
Partition: [msg@0] [msg@1] [msg@2] [msg@3] [msg@4] [msg@5] [msg@6] ...
             ↑                                      ↑
        consumer A                             consumer B
        прочитал до offset 1                   прочитал до offset 5
        (committed offset = 1)                 (committed offset = 5)
```

Offset — ключевой механизм для:
- **Отслеживания прогресса потребления** — consumer хранит последний committed offset.
- **Перемотки (replay)** — consumer может сбросить offset на 0 и перечитать всю историю.
- **Поиска конкретного сообщения** — используя .index и .timeindex файлы внутри сегмента.

### 2.4 Внутренняя структура сегмента: .log, .index, .timeindex

Каждый сегмент состоит из трёх файлов:

```
cars-0/
├── 00000000000000000000.log       ← сами данные (сообщения)
├── 00000000000000000000.index     ← offset → позиция в .log
└── 00000000000000000000.timeindex ← timestamp → offset
```

**.log файл** — содержит сообщения в формате record batches. Producer группирует сообщения в batch и отправляет одним сетевым запросом. Внутри .log файла каждый batch содержит:

| Поле | Описание |
|------|----------|
| baseOffset | Offset первого сообщения в batch-е |
| lastOffset | Offset последнего сообщения |
| count | Количество сообщений |
| position | Позиция batch-а в файле (в байтах) |
| CreateTime | Timestamp последнего сообщения |
| size | Размер batch-а в байтах |
| Messages | Список сообщений (key + value + headers) |

Пример (вывод DumpLogSegments):

```
baseOffset: 0 lastOffset: 6 count: 7 position: 0 CreateTime: 1586329540137 size: 173
| offset: 0 key: 2 payload: BMW
| offset: 1 key: 5 payload: Chevrolet
| offset: 2 key: 6 payload: Porsche
...
```

**.index файл** — разреженный индекс (sparse index) offset → позиция в .log. Зачем? Чтобы найти сообщение по offset, не нужно сканировать весь .log файл.

Алгоритм поиска сообщения с offset = k:
1. Бинарным поиском по именам файлов сегментов находим сегмент, содержащий k (baseOffset ≤ k).
2. В .index файле находим ближайшую запись с offset ≤ k. Она содержит позицию в .log файле.
3. От этой позиции линейно сканируем .log до offset = k.

Записи в .index добавляются не для каждого offset, а с интервалом, заданным параметром `log.index.interval.bytes` (по умолчанию 4096 байт). Это trade-off: реже индекс — меньше памяти, но дольше сканирование; чаще индекс — быстрее поиск, но больше памяти.

**.timeindex файл** — сопоставляет timestamp (CreateTime сообщения) → offset. Используется для поиска сообщений по времени (например, «покажи все сообщения с 10:00 до 10:05»). Принцип работы аналогичен .index: разреженная структура, запись добавляется с интервалом `log.index.interval.bytes`.

### 2.5 Retention: время жизни данных

Kafka не удаляет сообщения при чтении — они живут, пока не истечёт retention. Два типа политик:

| Параметр | Описание | Пример |
|----------|----------|--------|
| `retention.ms` | Удалять сегменты старше N миллисекунд | `604800000` = 7 дней |
| `retention.bytes` | Удалять старые сегменты, когда общий размер партиции превышает N | `1073741824` = 1 ГБ |

Можно комбинировать оба параметра: Kafka удалит сегмент, когда сработает первое из условий.

**Log compaction** — альтернативная политика для случаев, когда нужно хранить последнее значение для каждого ключа (например, таблица пользователей, CDC-потоки). При compaction Kafka оставляет только последнее сообщение для каждого уникального ключа, удаляя все предыдущие.

## 3. Write Path: путь сообщения от producer до партиции

### 3.1 Producer internals: что происходит при вызове send()

```java
// Код приложения
producer.send(new ProducerRecord<>("orders", "userId:123", "{\"amount\": 500}"));
```

Под капотом:

```
Приложение                  KafkaProducer                  Сеть               Брокер
    │                            │                          │                   │
    │ 1. send(record)            │                          │                   │
    ├───────────────────────────►│                          │                   │
    │                            │ 2. Serializer (key+val)  │                   │
    │                            │ 3. Partitioner (→ part.2)│                   │
    │                            │ 4. RecordAccumulator     │                   │
    │                            │    (буфер на партицию)   │                   │
    │                            │                          │                   │
    │                            │ 5. Sender thread         │                   │
    │                            │    (ждёт batch.size или  │                   │
    │                            │     linger.ms)           │                   │
    │                            │                          │                   │
    │                            │ 6. ProduceRequest───────►│                   │
    │                            │    (batch сообщений)     │ 7. Append to log  │
    │                            │                          │ 8. Replicate      │
    │                            │◄─── ProduceResponse ─────│ 9. ACK            │
    │                            │                          │                   │
    │◄── callback/future ───────┤                          │                   │
    │                            │                          │                   │
```

Разберём каждый шаг:

**Шаг 1-3: Сериализация и партиционирование**

KafkaProducer получает `ProducerRecord`. Первым делом:
- Key и value сериализуются в byte[] через настроенные Serializer-ы.
- Partitioner определяет, в какую партицию отправить сообщение.

Стратегии партиционирования:

| Стратегия | Когда использовать | Пример |
|-----------|-------------------|--------|
| **Key-based hash** (по умолчанию) | Нужен порядок по ключу | `murmur2(key) % numPartitions` |
| **Round-robin** (key = null) | Равномерная нагрузка | Случайная партиция |
| **Custom Partitioner** | Особая логика | Отправлять VIP-пользователей в отдельную партицию |

Важно: key-based партиционирование гарантирует, что все сообщения с одним ключом попадут в одну партицию, а значит — будут обработаны в порядке отправки.

**Шаг 4: RecordAccumulator — буфер-накопитель**

Ключевой компонент производительности. `RecordAccumulator` содержит отдельную очередь (Deque) для каждой партиции. Сообщения не отправляются немедленно, а накапливаются в batch-и.

Параметры, управляющие накоплением:

| Параметр | Описание | Значение по умолчанию |
|----------|----------|----------------------|
| `batch.size` | Максимальный размер batch-а в байтах | 16 384 (16 КБ) |
| `linger.ms` | Максимальное время ожидания перед отправкой неполного batch-а | 0 (отправлять сразу) |
| `buffer.memory` | Общий объём памяти для буферизации | 33 554 432 (32 МБ) |
| `max.block.ms` | Сколько ждать, если буфер заполнен | 60 000 (60 сек) |

**Аналогия: почтовый грузовик.** Вместо того чтобы отправлять каждое письмо отдельным рейсом, почтальон ждёт, пока накопится достаточное количество писем (batch.size) или истечёт время ожидания (linger.ms), и только тогда выезжает. Это экономит бензин (сетевые round-trips) и время (CPU на обработку запросов).

Увеличение `linger.ms` увеличивает задержку (latency), но повышает throughput и снижает нагрузку на сеть. Увеличение `batch.size` повышает throughput до определённого предела, за которым рост прекращается (упирается в пропускную способность сети/диска).

**Шаг 5-6: Sender thread и ProduceRequest**

`Sender` — это фоновый поток (daemon thread), который:
1. Периодически проверяет RecordAccumulator на наличие готовых batch-ей.
2. Группирует batch-и для одного брокера (даже из разных партиций).
3. Отправляет один ProduceRequest со всеми batch-ами.
4. Обрабатывает ответы и вызывает callbacks.

Важно: Sender отправляет данные только лидеру партиции. Если приложение не знает, какой брокер является лидером, оно запрашивает метаданные (MetadataRequest), кэширует их и обновляет периодически (`metadata.max.age.ms`, по умолчанию 5 минут).

**Шаг 7-9: Обработка на брокере и ACK**

Брокер получает ProduceRequest, дописывает batch в .log файл активного сегмента и реплицирует данные на follower-ов.

Уровни подтверждения (`acks`):

| `acks` | Поведение | Гарантии | Когда использовать |
|--------|-----------|----------|-------------------|
| `0` | Не ждать подтверждения | Никаких. Данные могут потеряться | Метрики, где потеря некритична |
| `1` | Ждать подтверждения только от лидера | Данные записаны на лидере, потеряются при сбое лидера до репликации | Большинство юзкейсов |
| `all` (или `-1`) | Ждать подтверждения от лидера + всех ISR-реплик | Данные не теряются, пока жив кворум ISR | Платежи, аудит, критические данные |

Совместно с `acks=all` используют параметр `min.insync.replicas` — минимальное количество реплик, которые должны подтвердить запись. Если в ISR меньше реплик, чем задано — запись отклоняется (NotEnoughReplicasException). Типичная конфигурация для production:

```
acks=all
min.insync.replicas=2
replication.factor=3
```

Это гарантирует: данные записаны минимум на 2 брокера (включая лидера), толерантность к потере 1 брокера.

### 3.2 Сжатие (compression) на стороне producer

Kafka поддерживает сжатие batch-ей до отправки:

| Кодек | Скорость | Степень сжатия | CPU |
|-------|----------|---------------|-----|
| `none` | Максимальная | Нет | Минимум |
| `lz4` | Высокая | Средняя | Низкий |
| `snappy` | Высокая | Средняя | Низкий |
| `gzip` | Средняя | Высокая | Средний |
| `zstd` | Средняя | Максимальная | Средний |

Сжатие задаётся параметром `compression.type`. Брокер хранит данные в сжатом виде «как есть», не распаковывая. Consumer получает сжатые batch-и и распаковывает их на своей стороне.

Выигрыш от сжатия: при `lz4` на реальных данных (JSON-логи) — экономия 60-80% сетевого трафика и дискового пространства, прирост throughput в 2-3 раза. CPU overhead минимален.

## 4. Replication Layer: как Kafka обеспечивает durability

### 4.1 Leader/Follower модель

Каждая партиция имеет ровно одного лидера и N follower-ов (где N = replication.factor − 1). Все операции чтения и записи идут через лидера:

```
                ┌─────────┐
   Producer ──► │ Leader  │ ◄── Consumer
    (write)     │ part.0  │     (read)
                └───┬──┬──┘
                    │  │ репликация
              ┌─────┘  └─────┐
              ▼              ▼
        ┌──────────┐  ┌──────────┐
        │ Follower │  │ Follower │
        │  brk 2   │  │  brk 3   │
        └──────────┘  └──────────┘
```

Follower-ы пассивно потребляют данные от лидера (pull model — follower сам запрашивает данные, как обычный consumer). Они не обслуживают клиентские запросы на запись или чтение (если не настроены consumer-ы для чтения из follower — в Kafka это возможно, но не типично для consistency).

### 4.2 ISR (In-Sync Replicas)

ISR — это множество реплик, которые «догнали» лидера. Реплика считается in-sync, если:
- Она активна (отвечает на запросы).
- Она «отстала» от лидера не более чем на `replica.lag.time.max.ms` (по умолчанию 30 секунд).

```
Leader offset: 12500
Follower A: 12500  ← in-sync (в ISR)
Follower B: 12500  ← in-sync (в ISR)
Follower C: 11000  ← out-of-sync! (отстал на 1500 сообщений или >30 сек)
```

ISR имеет критическое значение для durability: при `acks=all` производитель ждёт подтверждения от **всех ISR-реплик**, а не от всех настроенных follower-ов. Если одна реплика выпала из ISR — это не блокирует запись.

### 4.3 Leader election (выборы лидера)

Когда лидер партиции падает, контроллер кластера выбирает нового лидера из числа ISR-реплик. Процесс:

1. Брокер перестаёт отвечать на heartbeats в KRaft quorum.
2. Контроллер обнаруживает отказ.
3. Контроллер выбирает нового лидера для всех партиций упавшего брокера — только из ISR.
4. Контроллер рассылает LeaderAndIsrRequest всем брокерам — они обновляют свои метаданные.
5. Producers и consumers получают обновлённые метаданные и переключаются на нового лидера.

**Важно:** если ISR пуст (все follower-ы отстали или упали), включается unclean leader election. Параметр `unclean.leader.election.enable` (по умолчанию `false`) определяет, можно ли выбрать лидера из out-of-sync реплик. Если `false` — партиция становится недоступной до восстановления реплики из ISR. Если `true` — выбирается out-of-sync реплика, но данные могут быть потеряны (жертвуем durability ради доступности — классический CAP trade-off).

### 4.4 Механизм репликации: FetchRequest от follower

Репликация в Kafka работает через pull-модель (follower сам запрашивает данные), а не push (лидер пушит на follower). Это то же самое, что делает consumer:

```
Follower: "Дай мне данные, начиная с offset 12500"
Leader:   "Вот batch-и: offset 12500-12550, размер 8 КБ"
Follower: "Записал. Дай мне дальше, с offset 12551"
```

Почему pull, а не push? Причины:
- Follower сам знает свой темп и не перегружается.
- Меньше сложности на лидере (не нужно отслеживать состояние follower-ов).
- Использует тот же Fetch API, что и consumer — меньше кода, отлаженный механизм.

## 5. Read Path: как consumer читает данные

### 5.1 Pull-модель: consumer запрашивает, брокер отдаёт

Consumer не получает данные пассивно. Он отправляет FetchRequest брокеру:

```
Consumer: "Дай мне данные из topic=orders, partition=0, начиная с offset=12500"
Broker:   "Вот batch: offset 12500-12550"
Consumer: "Обработал. Дай мне дальше, с offset=12551"
```

Параметры consumer, влияющие на fetch:

| Параметр | Описание | Значение по умолчанию |
|----------|----------|----------------------|
| `fetch.min.bytes` | Минимальный объём данных, который брокер должен вернуть в ответе | 1 |
| `fetch.max.wait.ms` | Максимальное время ожидания на брокере, если min.bytes не набран | 500 |
| `max.partition.fetch.bytes` | Максимальный размер данных с одной партиции в одном запросе | 1 048 576 (1 МБ) |
| `fetch.max.bytes` | Общий максимум данных в одном FetchResponse | 52 428 800 (50 МБ) |

Аналогия с `fetch.min.bytes` + `fetch.max.wait.ms`: как заказ в ресторане «принесите хотя бы 3 блюда, но если через 5 минут их нет — несите что есть». Это trade-off latency vs throughput.

### 5.2 Consumer Groups и параллелизм

Consumer-ы объединяются в группы (consumer groups) — логические объединения consumer-ов, которые вместе читают один или несколько топиков. Каждая партиция в группе назначается ровно одному consumer. Это гарантирует, что сообщения не дублируются внутри группы:

```
Топик "orders" (3 партиции)
┌──────────┐  ┌──────────┐  ┌──────────┐
│Partition 0│  │Partition 1│  │Partition 2│
└─────┬─────┘  └─────┬─────┘  └─────┬─────┘
      │               │               │
   ┌──▼───┐      ┌───▼──┐      ┌───▼──────┐
   │Cons. A│      │Cons. B│      │Cons. C   │
   └───────┘      └───────┘      └──────────┘
         Consumer Group "order-processors"
```

**Правило масштабирования:** количество consumer-ов в группе ≤ количество партиций. Если consumer-ов больше, чем партиций — лишние consumer-ы простаивают (им не достаётся партиций).

Если consumer падает — его партиции перераспределяются между оставшимися (rebalance).

### 5.3 Offset management: как consumer помнит, где остановился

Consumer отслеживает свой прогресс через offset — числовой указатель на последнее обработанное сообщение. Offset-ы хранятся во внутреннем топике `__consumer_offsets` (создаётся автоматически). Варианты работы с offset:

```java
// 1. Автоматический commit (enable.auto.commit=true)
// Kafka коммитит offset каждые auto.commit.interval.ms
// Плюс: просто. Минус: возможен at-most-once

// 2. Ручной commit после обработки
consumer.commitSync(); // синхронно, ждём результат
// или
consumer.commitAsync(); // асинхронно, не блокируемся

// 3. Ручное управление offset — полный контроль
consumer.seek(new TopicPartition("orders", 0), 12500);
```

**At-least-once vs at-most-once vs exactly-once:**

| Паттерн | Как достичь | Что с гарантией |
|---------|------------|-----------------|
| **At-most-once** | Commit ДО обработки. При сбое — уже committed, повторно не обработается | Сообщение может быть потеряно |
| **At-least-once** | Commit ПОСЛЕ обработки. При сбое между обработкой и commit — повтор | Сообщение обработается минимум 1 раз, возможны дубликаты |
| **Exactly-once** | Kafka Transactions API (idempotent producer + transactional consumer) | Сообщение обработается ровно 1 раз |

### 5.4 Rebalance: перераспределение партиций

Когда consumer добавляется в группу или покидает её (по таймауту, `session.timeout.ms`), запускается **rebalance** — процесс перераспределения партиций между consumer-ами.

**Классический протокол (group.protocol=classic)** — двухфазный процесс:

```
Фаза 1: JoinGroup
  - Все consumer-ы отправляют JoinGroup
  - Coordinator ждёт ВСЕХ участников
  - Выбирает лидера группы (один из consumer-ов)
  
Фаза 2: SyncGroup  
  - Лидер группы вычисляет новое распределение партиций
  - Рассылает назначения через SyncGroup
  - Consumer-ы получают свои партиции
```

Проблема классического протокола: **stop-the-world**. Пока идёт rebalance, ВСЕ consumer-ы в группе прекращают обработку. На больших группах (30+ consumer-ов) rebalance может занимать десятки секунд.

**Новый протокол (group.protocol=consumer, Kafka 4.0+)** — серверная модель:

```
- Coordinator (на брокере) сам вычисляет распределение
- Серверное назначение (server-side assignment, group.remote.assignor)
- Инкрементальный rebalance: перемещаются только нужные партиции
- Consumer-ы, не затронутые rebalance-ом, продолжают обработку
- Commit offset-ов разрешён во время rebalance
```

Преимущества нового протокола:
- Rebalance занимает 2-4 секунды вместо 25-45 секунд (на 30 consumer-ах).
- Снижение координационного сетевого трафика на 60-70%.
- Устойчивость к «медленным» consumer-ам (один тормозной consumer больше не блокирует всю группу).

## 6. Performance optimizations: что делает Kafka быстрой

### 6.1 Zero-Copy: данные не копируются в userspace

Когда consumer запрашивает данные, брокеру нужно прочитать их с диска и отправить по сети. Без оптимизаций это выглядит так:

```
Традиционный путь (4 копирования):
  Диск → Kernel Buffer → Application Buffer → Socket Buffer → NIC
                ↑                      ↑
           read() syscall        write() syscall
              (context             (context
               switch)              switch)
```

**Kafka с Zero-Copy (использует `sendfile()` system call):**

```
Zero-Copy путь (2 копирования, 0 копирований через CPU):
  Диск → Kernel Buffer (Page Cache) ──sendfile()──► Socket Buffer → NIC
                ↑
        только DMA-копирование,
        CPU не копирует данные
```

Linux системный вызов `sendfile()` передаёт данные напрямую из page cache в сокетный буфер, минуя userspace. Данные не пересекают границу kernel/user — экономия 2 контекстных переключений и 2 копирований на каждый запрос.

**Аналогия:** вместо того чтобы переносить книги с одного стеллажа (диск) на стол читателя (userspace), а потом на другой стеллаж (socket), библиотекарь (ядро) переставляет их напрямую, даже не заходя в читальный зал.

Результат: consumer получает данные с диска на скоростях, близких к пропускной способности сетевой карты, при минимальной загрузке CPU.

### 6.2 Page Cache: чтение из оперативной памяти, а не с диска

Kafka **не кэширует данные в JVM heap**. Вместо этого она полагается на OS page cache — кэш файловой системы в ядре операционной системы.

```
  ┌────────────────────────────┐
  │        JVM Heap            │
  │  Kafka (логика, метаданные)│     ← данные НЕ здесь
  └────────────────────────────┘
  ┌────────────────────────────┐
  │     OS Page Cache          │
  │  (kernel memory)           │     ← данные ЗДЕСЬ
  │   ┌───────────────────┐    │
  │   │ Недавние batch-и   │    │
  │   │ (горячие данные)   │    │
  │   └───────────────────┘    │
  └────────────────────────────┘
  ┌────────────────────────────┐
  │          Диск              │     ← холодные данные
  └────────────────────────────┘
```

**Почему page cache, а не in-memory кэш:**

- **Нет double-buffering:** данные не находятся одновременно в page cache и JVM heap. Экономия памяти.
- **GC-friendly:** Kafka не создаёт множество объектов — меньше pressure на garbage collector.
- **Автоматическое управление:** ядро ОС само решает, что держать в page cache (LRU), и flushing на диск делает ядро, а не Kafka.
- **Recovery:** при перезапуске брокера page cache восстанавливается по мере чтения с диска — «холодный старт» безопасен.

Большинство production-нагрузок Kafka работают в режиме, когда все «горячие» данные (последние минуты/часы) находятся в page cache. Это даёт скорости чтения, сравнимые с чтением из RAM — микросекундные задержки.

### 6.3 Batching на всех уровнях

Batching — сквозная оптимизация, работающая на трёх уровнях:

**Producer → Broker:**
- RecordAccumulator накапливает batch-и до `batch.size` или `linger.ms`
- Sender thread отправляет один ProduceRequest = много batch-ей для разных партиций одного брокера

**Broker → Disk:**
- Batch записывается в .log файл одной операцией, как единый блок
- Метаданные batch-а (offset-ы, count) — одни на batch, а не на каждое сообщение

**Broker → Consumer:**
- Consumer получает batch целиком
- FetchRequest забирает сразу много batch-ей

### 6.4 Sequential I/O и отсутствие random access

Ещё раз подчеркнём: весь дисковый I/O в Kafka — sequential. Это даёт:

- HDD: ~100 МБ/с (sequential) vs ~ 1 МБ/с (random, 4K блоки)
- SSD: ~500 МБ/с (sequential) vs ~ 40 МБ/с (random, 4K блоки)
- Меньше head movement (HDD), меньше wear (SSD)
- Лучшая работа OS prefetch и кэширования

Даже compaction (удаление дубликатов по ключу) работает sequential: создаётся новый чистый (clean) сегмент, а старый удаляется.

## 7. Control Plane: метаданные и координация

### 7.1 KRaft (Kafka 4.0+, ранее ZooKeeper)

Современная Kafka управляет метаданными через KRaft — реализацию Raft-консенсуса внутри самой Kafka. От 3 до 5 контроллеров (controller nodes) образуют quorum, который хранит все метаданные кластера во внутреннем топике `__cluster_metadata`:

```
KRaft Quorum (3 контроллера)
┌──────────┐   ┌──────────┐   ┌──────────┐
│ Active   │◄──┤ Follower │◄──┤ Follower │
│Controller│   │          │   │          │
└────┬─────┘   └──────────┘   └──────────┘
     │ __cluster_metadata topic
     │ (единственная партиция, реплицируется между контроллерами)
     │
     │ FetchRequest (брокеры получают метаданные как consumer-ы)
     ▼
┌──────────┐   ┌──────────┐   ┌──────────┐
│Broker 1  │   │Broker 2  │   │Broker 3  │
└──────────┘   └──────────┘   └──────────┘
```

Метаданные кластера (топики, партиции, ACL, конфигурации, регистрация брокеров) хранятся и реплицируются внутри `__cluster_metadata` — обычного Kafka-топика.

Почему KRaft лучше ZooKeeper:

| Операция | ZooKeeper | KRaft |
|----------|-----------|-------|
| Создание топика | Множество ZK round-trip-ов, watch на каждом брокере | Один append в metadata log |
| Controller failover | Минуты на больших кластерах (читать все znodes) | Секунды (log уже у нового лидера) |
| Регистрация брокера | Ephemeral znode + watch propagation | RegisterBrokerRecord в log |
| Партиций на кластер | ~200 000 | 2 000 000+ |
| Скорость failover | ~10x медленнее | ~10x быстрее |

**Как работает consensus:** KRaft использует pull-based Raft (в отличие от классического push-based). Follower-ы сами запрашивают записи из лога у лидера. Leader election — стандартный Raft: лидер периодически шлёт heartbeats; если follower не получает heartbeat в течение election timeout, он становится кандидатом и запрашивает голоса. Кандидат, набравший большинство, становится новым лидером.

### 7.2 Распространение метаданных на брокеры

Брокеры получают метаданные кластера через обычный FetchRequest (как consumer-ы):

```
Controller (лидер quorum) → Broker: "вот новые метаданные: создан топик orders, 3 партиции"
Broker: "Принял. Обновил локальную копию metadata log."
```

Брокер поддерживает локальную копию metadata log, применяет записи по порядку и обновляет in-memory кэш метаданных. Брокер может немного отставать — это не нарушает корректность, только его собственное «видение» кластера.

## 8. Энд-ту-энд: полный lifecycle сообщения

Соберём всё вместе — путь одного сообщения от producer до consumer:

```
Время (мс)   Событие
──────────────────────────────────────────────────────────
   0         Producer.send(record)
   1         Serializer: key → 4 bytes, value → 150 bytes
   2         Partitioner: key="user:123" → hash → partition 1
   3         RecordAccumulator: добавил в очередь partition-1
   4-14       Ждём. За это время накопилось ещё 50 сообщений
             в эту же партицию. Batch: 51 сообщение, 8 КБ
  15         Sender: отправляем ProduceRequest на broker-2
             (broker-2 = leader для partition-1)

             === НА БРОКЕРЕ ===

  16         Broker-2: получил ProduceRequest. Проверяет:
             - Я лидер для partition-1? Да.
             - Актуальные ли метаданные? Да.
  17         Append: batch → активный сегмент .log файла
             Offset присвоен: 12500-12550
  18         ReplicaFetcher на broker-1: FetchRequest
             "дай мне offset 12500 от topic=orders, part=1"
  19         Broker-2: вот batch, offset 12500-12550
  20         Broker-1: записал batch. ISR теперь [2, 1]
  21         Broker-1 → Broker-2: "я догнал, offset=12550"
  22         Broker-2: ISR подтверждение получено
             (acks=all + min.insync.replicas=2 → ОК)
  23         Broker-2 → Producer: ProduceResponse (OK, baseOffset=12500)

             === ОБРАТНО НА PRODUCER ===

  24         Sender получил ответ. Callback: "message sent to part=1, offset=12500"
  25         Future.complete(). Приложение знает: сообщение записано.

──────────────────────────────────────────────────────────

Consumer (Consumer Group "order-processors"):

  26         Consumer.poll(100ms)
  27         FetchRequest: topic=orders, part=1, offset=lastCommitted (10000)
  28         Broker-2 (лидер): page cache hit!
             Zero-copy sendfile: page cache → NIC
  29         Consumer: FetchResponse. Batch: offset 10001-10500
  30         Consumer обрабатывает 500 сообщений, по одному
  31         Consumer.commitSync(): offset=10501 записан в __consumer_offsets

──────────────────────────────────────────────────────────
Итого: ~25 мс от send() до ack при acks=all (внутри одного ЦОД)
       + Consumer читает с задержкой ~0 мс (для уже записанных данных)

При acks=1: ~2-5 мс
При acks=0: <1 мс
```

## 9. CAP-теорема и позиционирование Kafka

### 9.1 Куда Kafka в CAP-треугольнике

Kafka по умолчанию выбирает **Consistency + Partition Tolerance (CP)** в рамках партиции:

- **Consistency:** строгий порядок в пределах партиции (по offset). Все записи проходят через лидера. При `acks=all` + `min.insync.replicas` — durability гарантирована.
- **Partition Tolerance:** система продолжает работу при потере сетевых соединений между брокерами (до определённого предела — пока жив кворум ISR).
- **Availability** может быть принесена в жертву: если ISR упал ниже `min.insync.replicas`, партиция становится **недоступной для записи** (NotEnoughReplicasException). Это осознанный trade-off: durability > availability.

Однако можно переключить поведение в AP-режим:
- `acks=1` + `unclean.leader.election.enable=true` — Kafka становится AP-системой (доступность ценой возможной потери данных).

### 9.2 Consistency models

Kafka предоставляет **per-partition ordering**:

- **Гарантия порядка:** сообщения в пределах одной партиции доставляются consumer-у строго в порядке offset-ов (порядок записи = порядок чтения). Это causal consistency на уровне партиции.
- **Между партициями порядка нет:** partition 0 и partition 1 никак не синхронизированы. Если приложению нужен глобальный порядок — используй **одну партицию** (но теряешь параллелизм).

Гарантии доставки:

| Модель | Producer | Consumer | Описание |
|--------|----------|----------|----------|
| **At-most-once** | `acks=0` | Auto-commit до обработки | Сообщение может потеряться |
| **At-least-once** | `acks=1` или `acks=all` | Commit после обработки | Сообщение может дублироваться |
| **Exactly-once** | `enable.idempotence=true` + `transactional.id` | `isolation.level=read_committed` | Ровно 1 раз (KIP-98, Kafka 0.11+) |

**Exactly-once semantics (EOS):** Kafka реализует через:
- **Idempotent Producer** (`enable.idempotence=true`): каждое сообщение получает Producer ID (PID) + sequence number. Брокер дедуплицирует сообщения с одинаковым PID + sequence.
- **Transactional Producer** (`transactional.id`): позволяет атомарно записать в несколько партиций и атомарно commit offset + consume.
- **Transactional Consumer** (`isolation.level=read_committed`): видит только committed-сообщения, игнорируя aborted транзакции.

## 10. Design principles: почему архитектура именно такая

Соберём ключевые дизайн-принципы, которые объясняют каждое архитектурное решение:

| Принцип | Что даёт | Где проявляется |
|---------|----------|-----------------|
| **Append-only log** | Sequential I/O, immutable storage, простая репликация | Partition → Segment → .log |
| **Dumb broker, smart client** | Брокеры не занимаются бизнес-логикой, не тратят CPU | Consumer сам управляет offset |
| **Pull-модель (consumer/follower pull)** | Backpressure через темп самого consumer, упрощение брокера | FetchRequest, репликация |
| **Zero-Copy + Page Cache** | Данные не копируются → max throughput при min CPU | sendfile(), файловая система |
| **Batching на всех уровнях** | Каждый уровень амортизирует overhead множества сообщений | RecordAccumulator, ProduceRequest |
| **Partition-based масштабирование** | Горизонтальный scale через добавление партиций | Topic → Partition |
| **ISR вместо кворумной записи** | Durability без блокировки на медленные реплики | `acks=all` + ISR |
| **Metadata-as-log (KRaft)** | Единый механизм репликации для данных и метаданных | __cluster_metadata |

Эти принципы — не компромиссы, а осознанные trade-off-ы, проверенные на масштабах LinkedIn (триллионы сообщений в день), Uber (миллионы GPS-событий/мин) и Netflix (петабайты событий/день).

## 11. Заключение

**Kafka — это не message queue.** Это распределённая платформа хранения и доставки потоков событий, построенная на append-only логах, партиционировании и pull-репликации. Её архитектура — результат последовательного применения нескольких фундаментальных инженерных решений:

1. **Хранение как sequential log:** вместо B-tree или index-organized storage — простой append-only файл.
2. **Репликация через pull:** follower сам потребляет, как consumer. Тот же Fetch API.
3. **Zero-Copy + Page Cache:** отказ от копирования данных и in-memory кэширования ради CPU-efficiency.
4. **Batching и compression:** амортизация сетевых round-trip и дискового I/O.
5. **KRaft вместо ZooKeeper:** metadata как ещё один лог, единый механизм репликации.
6. **Server-Side Consumer Protocol (4.0+):** отказ от stop-the-world rebalance-ов в пользу инкрементальной миграции партиций.

Результат: система, которая записывает и отдаёт миллионы сообщений в секунду на commodity-«железе», хранит их столько, сколько нужно (от секунд до лет), позволяет перечитывать историю, распределяет нагрузку через партиции и устойчива к отказам (при правильной конфигурации `acks=all` + `min.insync.replicas`).

**Что дальше:** в [03-core-concepts.md](./03-core-concepts.md) мы разберём ключевые абстракции и гарантии: модель данных, exactly-once семантику, механизмы координации consumer groups, а также углублённо посмотрим на CAP-позиционирование и consistency models.
