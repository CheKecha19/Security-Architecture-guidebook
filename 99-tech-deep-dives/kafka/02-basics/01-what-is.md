# Что такое Apache Kafka? Введение для начинающих

> **Нижняя строка:** Apache Kafka — это распределённая платформа событийного стриминга (event streaming), которая позволяет публиковать, хранить, обрабатывать и перечитывать потоки событий в реальном времени. Проще говоря, это высокоскоростной конвейер и долговременное хранилище для данных, которые поступают непрерывно.

---

## 1. ELI5: Объясняем Kafka на пальцах

Представь себе огромный аэропорт.

- Самолёты (приложения, датчики, базы данных) постоянно прилетают и улетают.
- У каждого самолёта есть багаж — это **события** (events): «пользователь кликнул кнопку», «датчик показал температуру 23°C», «платёж на сумму 500₽ прошёл».
- Багаж отправляется на **конвейерную ленту** (Kafka topic) с биркой (key), которая говорит, к какому рейсу он относится.
- Получатели (другие приложения, аналитические системы, базы данных) забирают багаж с ленты — каждый со своей скоростью и в своём порядке.
- Конвейер ничего не выбрасывает сразу — багаж лежит на ленте столько, сколько нужно. Если получатель опоздал — он может забрать багаж позже.
- Лента не одна — их много (**партиции, partitions**), и каждая обслуживается отдельным работником (**брокером, broker**). Если один работник заболел — его сменяет другой с копией того же багажа (**репликация**).

**Kafka — это система, которая гарантирует, что ни один чемодан (событие) не потеряется, а каждый получатель получит именно те чемоданы, которые ему нужны, в правильном порядке и вовремя.**

### Другая аналогия: нервная система организма

Официальная документация Kafka сравнивает событийный стриминг с центральной нервной системой человека. Мозг (приложение-обработчик) получает сигналы от рецепторов (producers): «горячо», «давление поднялось», «мышца сократилась». Нервные волокна (Kafka) передают сигналы мгновенно и надёжно. Мозг реагирует (consumers обрабатывают события) — отдёргивает руку, запускает бизнес-логику, отправляет уведомление.

## 2. Что такое Kafka простыми словами

### Определение

**Apache Kafka** — это:

- **Распределённая (distributed)** — работает на кластере из нескольких серверов, а не на одной машине.
- **Событийно-ориентированная (event-driven)** — оперирует событиями (events/records/messages), а не запросами.
- **Платформа стриминга (streaming platform)** — не просто передаёт сообщения, а хранит их и позволяет обрабатывать потоки данных.
- **С открытым исходным кодом (open-source)** — написана на Java/Scala, поддерживается Apache Software Foundation, лицензия Apache 2.0.

В одном предложении: **Kafka — это commit log на стероидах, распределённый и масштабируемый до миллионов сообщений в секунду.**

### Три ключевые способности

Kafka объединяет три функции, которые обычно реализуются разными системами:

| # | Функция | Что это значит |
|---|---------|----------------|
| 1 | **Публикация и подписка (Pub/Sub)** | Приложения пишут события в Kafka и читают их оттуда. Producers и consumers полностью развязаны (decoupled) и не знают друг о друге. |
| 2 | **Долговременное хранение (Storage)** | События хранятся на диске столько, сколько настроишь — минуты, дни, годы. В отличие от очередей сообщений, события не удаляются после прочтения. |
| 3 | **Обработка потоков (Stream Processing)** | События можно трансформировать, фильтровать, агрегировать прямо на лету через Kafka Streams API или внешние процессоры (Flink, Spark). |

### Кто создал и зачем

Kafka родилась в LinkedIn в 2010 году. Компании требовалась система, которая собирает данные о поведении пользователей (клики, просмотры страниц, поисковые запросы) и доставляет их всем заинтересованным системам: мониторингу, аналитике, рекомендательным движкам, Hadoop-кластеру. Традиционные очереди (ActiveMQ, RabbitMQ) не справлялись с объёмом — LinkedIn генерировал около 1,4 триллиона сообщений в день к моменту открытия исходного кода Kafka.

Создатели: **Jay Kreps**, **Neha Narkhede** и **Jun Rao** — инженеры LinkedIn. Название выбрано в честь писателя Франца Кафки: как шутил Jay Kreps, потому что «это система, оптимизированная для записи» (writing), а Kafka был писателем.

### Текущий статус

- Стабильная версия: **4.2.0** (февраль 2026)
- Более 80% компаний из Fortune 100 используют Kafka
- Часть Apache Software Foundation с 2012 года
- Экосистема включает десятки коннекторов, клиентов на всех языках, managed-сервисы от AWS (MSK), Confluent Cloud, Red Hat и других

## 3. Core Purpose: для чего на самом деле нужна Kafka

### Основное назначение

Kafka решает одну фундаментальную проблему: **как надёжно и быстро перемещать данные между множеством систем, когда данные поступают непрерывно, а системы могут появляться и исчезать.**

Традиционный подход — point-to-point интеграции:

```
Система A → Система B
Система A → Система C
Система B → Система D
Система C → Система D
```

Каждое соединение — это отдельный код, отдельная точка отказа, отдельный формат данных. При N системах количество соединений растёт как **N × (N−1)**. Добавление новой системы требует переписывания всех существующих интеграций.

**С Kafka архитектура выглядит иначе:**

```
Producer 1 ─┐                    ┌─ Consumer 1 (мониторинг)
Producer 2 ─┤                    ├─ Consumer 2 (аналитика)
Producer 3 ─┼── Apache Kafka ────┼─ Consumer 3 (поисковый индекс)
  ...       │                    │─ Consumer 4 (архив в S3/HDFS)
Producer N ─┘                    └─ Consumer 5 (рекомендации)
```

Kafka становится **центральной нервной системой данных**:
- Producers пишут события в Kafka
- Consumers читают события из Kafka
- Ни producers, ни consumers не знают друг о друге
- Новый consumer подключается без изменений на стороне producer

### 8 основных сценариев использования

#### 1. Обмен сообщениями (Messaging)
Замена традиционных брокеров сообщений (RabbitMQ, ActiveMQ). Kafka даёт лучшую пропускную способность, встроенное партиционирование, репликацию и отказоустойчивость «из коробки». Подходит для крупномасштабной обработки сообщений между сервисами.

*Пример:* сервис заказов публикует событие «заказ создан», а сервисы доставки, уведомлений, биллинга и аналитики независимо читают это событие.

#### 2. Отслеживание активности на сайте (Website Activity Tracking)
Исходный use case LinkedIn. Каждое действие пользователя (просмотр страницы, клик, поиск, лайк) — это событие. Kafka собирает их в реальном времени и доставляет системам мониторинга, рекомендаций, A/B-тестирования и offline-аналитики (Hadoop, Spark).

*Пример:* интернет-магазин отслеживает, какие товары просматривают пользователи, чтобы мгновенно обновлять рекомендации «с этим также смотрят».

#### 3. Метрики и мониторинг (Metrics)
Агрегация операционных метрик из распределённых приложений: CPU, память, задержки, количество запросов. Kafka централизует поток метрик для Prometheus, Grafana, дашбордов и алертинга.

#### 4. Агрегация логов (Log Aggregation)
Сбор логов с сотен серверов в центральное хранилище. Kafka даёт более низкую задержку и лучшую надёжность по сравнению с Flume или Scribe. Логи попадают в ELK (Elasticsearch + Logstash + Kibana) или Loki для анализа.

#### 5. Потоковая обработка (Stream Processing)
Многоступенчатые пайплайны обработки данных: сырые события → очистка → обогащение → агрегация → сохранение. Kafka Streams позволяет делать это без внешних кластеров (лёгкая embedded-библиотека на Java).

*Пример:* новостной агрегатор читает RSS-ленты → очищает и дедуплицирует контент → классифицирует по темам → рекомендует пользователю.

#### 6. Событийное sourcing (Event Sourcing)
Архитектурный паттерн, где состояние приложения не хранится как «текущая версия» объекта, а восстанавливается из цепочки всех событий, которые с ним произошли. Kafka с её неизменяемым (immutable) логом — идеальный backend для такого подхода.

*Пример:* банковский счёт. Вместо хранения «баланс: 1000₽» хранятся события: «+500₽», «−200₽», «+700₽». Баланс вычисляется как сумма событий. Полная история доступна для аудита.

#### 7. Commit Log для распределённых систем
Kafka выступает внешним журналом (log), который помогает реплицировать данные между узлами распределённой системы и восстанавливать состояние упавших узлов. Log Compaction (сжатие лога) хранит только последнее значение для каждого ключа — ключевая фича для этого сценария.

#### 8. Streaming ETL
Kafka Connect (source и sink коннекторы) обеспечивает непрерывный импорт/экспорт данных между Kafka и внешними системами: PostgreSQL, MongoDB, Elasticsearch, S3, Snowflake. Плюс Single Message Transforms (SMT) для простых преобразований на лету.

## 4. Когда использовать Kafka

Kafka — правильный выбор, когда выполняется **большинство** из этих условий:

| Критерий | Почему Kafka подходит |
|----------|----------------------|
| **Высокая пропускная способность** | Сотни тысяч — миллионы событий в секунду, гигабайты данных |
| **Множественные независимые consumers** | 5, 10, 50 сервисов читают одни и те же события — каждый со своим offset |
| **Необходимость replay (перечитывания) событий** | «Отмотать» историю на месяц назад и пересчитать аналитику заново |
| **Долговременное хранение событий** | Данные нужны неделями или месяцами, а не «прочитал и забыл» |
| **Высокая доступность (HA)** | Данные не должны теряться даже при падении сервера |
| **Декаплинг множества сервисов** | Десятки или сотни микросервисов разных команд |
| **Сквозное шифрование и аудит** | Immutable лог для compliance (GDPR, PCI-DSS, SOX) |
| **Рост системы** | Сегодня 3 сервиса, завтра 15, через месяц 50 |

### Конкретные индикаторы зрелости для внедрения Kafka:

- Количество событий: **> 10 000 в день** (нижняя граница осмысленности)
- Количество consumers: **≥ 3 независимых сервиса**
- Необходимость replay: **есть бизнес-требование «пересчитать за прошлый период»**
- Команда: **есть или планируется выделенный инженер, понимающий распределённые системы**

## 5. Когда НЕ использовать Kafka

Kafka — это мощный, но сложный инструмент. Его внедрение несёт операционные издержки: минимум 3 брокера для production, мониторинг, управление партициями, consumer group rebalancing, disk management, экспертиза команды.

**Правило большого пальца: если твою задачу решает PostgreSQL LISTEN/NOTIFY, Redis Pub/Sub, SQS или простой cron — бери их. Не усложняй.**

### 5 сценариев, где Kafka — overkill

#### Сценарий 1: Низкий объём (< 10 000 сообщений в день)
При 2 000 сообщений в день ты обрабатываешь 1,4 сообщения в минуту. Инфраструктурный overhead Kafka (брокеры, партиции, consumer groups, мониторинг) не оправдан.

*Что использовать вместо:*
- **PostgreSQL как очередь** с advisory locks и `SELECT ... FOR UPDATE SKIP LOCKED`
- **AWS SQS** / **GCP Pub/Sub** — managed-очереди без инфраструктурных забот
- **Redis Lists** (BLPOP/BRPOP) — простейшая очередь «из коробки»

#### Сценарий 2: Fire-and-forget уведомления
Типичные индикаторы набора текста в чате, live-дашборды, уведомления «пользователь онлайн» — эти сообщения не нуждаются в сохранении. Если получатель пропустил сигнал «кто-то печатает…» — никто не заметит.

*Что использовать вместо:*
- **Redis Pub/Sub** — fire-and-forget по определению, sub-millisecond latency, ноль operational complexity
- **WebSocket напрямую** — если потребитель один и это браузер

#### Сценарий 3: Request-Reply паттерны
Сервис A отправляет запрос, сервис B отвечает на другом топике, сервис A коррелирует по ID. Это работает, но идёт вразрез с асинхронной природой Kafka: сложность корреляции, задержки батчинга, response timeouts.

*Что использовать вместо:*
- **HTTP / gRPC** — проще, быстрее, легче отлаживать
- **NATS** — если нужен именно асинхронный request-reply, NATS делает это нативно

#### Сценарий 4: Простая пакетная обработка (Batch ETL)
Ночной ETL-джоб: извлёк данные из БД → трансформировал → залил в S3. Добавление Kafka в середину добавляет инфраструктуру, точки отказа и exactly-once конфигурацию ради одного потребителя.

*Признаки, что ты используешь Kafka как файловую систему:* один producer, один consumer, поллинг раз в час, ожидание маркера «конец батча».

*Что использовать вместо:*
- **Cron + скрипт**
- **Apache Airflow / Dagster** — для оркестрации batch-пайплайнов

#### Сценарий 5: Два сервиса
Два сервиса нуждаются в асинхронной коммуникации. Kafka добавляет: 3+ брокерных ноды, Schema Registry, мониторинг, on-call rotation, управление партициями. Несоразмерно.

*Что использовать вместо:*
- **AWS SQS** — нет инфраструктуры, встроенные retry, dead-letter queue, pay-per-message
- **Webhooks** — если сервис B отдаёт HTTP endpoint, вебхук с retry-логикой покрывает 90% потребностей
- **Redis / RabbitMQ** — классический брокер на одну инсталляцию

### Дерево принятия решений

```
Нужно передавать данные между сервисами?
│
├─ < 10 000 сообщений/день? ────→ PostgreSQL, SQS, Redis
├─ Fire-and-forget? ──────────────→ Redis Pub/Sub, WebSocket
├─ Request-reply? ────────────────→ HTTP, gRPC, NATS
├─ Один consumer, batch? ────────→ Cron, Airflow
├─ Всего два сервиса? ───────────→ SQS, вебхуки, RabbitMQ
│
└─ ВЫСОКИЙ объём + МНОГО consumers + НУЖЕН replay ─→ KAFKA ✅
```

## 6. Kafka vs «обычная очередь сообщений»

Новички часто путают Kafka с RabbitMQ или ActiveMQ. Это понятно: и то и другое передаёт сообщения. Но разница принципиальная.

| Характеристика | Традиционная очередь (RabbitMQ) | Apache Kafka |
|---------------|----------------------------------|--------------|
| **Модель** | Smart broker, dumb consumer | Dumb broker, smart consumer |
| **Хранение сообщений** | Удаляются после подтверждения (ack) | Хранятся на диске согласно retention policy |
| **Порядок сообщений** | Глобальный FIFO в очереди | Порядок гарантирован только внутри партиции |
| **Replay** | Невозможен (сообщение ушло — и всё) | Да, любой consumer может перечитать историю с любого offset |
| **Пропускная способность** | Тысячи — десятки тысяч msg/s | Сотни тысяч — миллионы msg/s |
| **Масштабирование** | Вертикальное (добавить CPU/RAM) | Горизонтальное (добавить брокеров, партиций) |
| **Множественные consumers** | Каждое сообщение — одному consumer | Каждый consumer читает ВСЕ сообщения (свой offset) |
| **Протокол** | AMQP | Бинарный TCP-протокол, оптимизированный под батчинг |
| **Операционная сложность** | Низкая (один узел — ок) | Высокая (кластер, партиции, ребалансировка) |

**Грубая аналогия:** RabbitMQ — это почтальон, который доставляет письмо один раз одному адресату. Kafka — это газетный киоск: газеты (события) лежат на полке, каждый может купить любую газету в любое время, хоть вчерашнюю.

## 7. Как всё устроено в Kafka: 30-секундный ликбез

Не углубляясь (этому посвящена статья [02-how-it-works.md](./02-how-it-works.md)), вот минимальный набор понятий:

| Термин | Что такое | Аналогия |
|--------|----------|----------|
| **Event (событие)** | Запись о том, что что-то произошло: key, value, timestamp, headers | Строка в журнале: «12:05, касса №3, продано молоко, 89₽» |
| **Topic (топик)** | Именованный поток событий, аналог таблицы в БД или папки в ФС | Конвейерная лента конкретного рейса |
| **Partition (партиция)** | Часть топика, физически лежащая на конкретном брокере. События внутри партиции строго упорядочены | Отдельная дорожка конвейера |
| **Producer** | Приложение, которое пишет события в топик | Сотрудник, кладущий багаж на ленту |
| **Consumer** | Приложение, которое читает события из топика | Получатель багажа |
| **Consumer Group** | Группа consumers, которые делят между собой партиции топика. Каждое событие доставляется ровно одному consumer внутри группы | Бригада грузчиков: каждый берёт свой чемодан, никто не дублируется |
| **Broker** | Сервер Kafka, хранящий партиции и обрабатывающий запросы | Работник аэропорта, обслуживающий дорожки |
| **Offset** | Порядковый номер события внутри партиции. Consumer сам управляет своим offset | «Я остановился на чемодане №1042, продолжаю с №1043» |
| **Retention** | Как долго Kafka хранит события (по времени или размеру) | «Багаж хранится 7 дней, потом утилизируется» |
| **Replication** | Копирование партиции на несколько брокеров. Один — leader, остальные — followers | Если работник заболел, его сменщик точно знает, какой багаж уже отправлен |

## 8. Экосистема Kafka: взгляд с высоты

Kafka — не монолит. Это ядро плюс расширения:

```
                    ┌─ Kafka Connect ──── внешние системы (БД, S3, Elasticsearch)
                    │
Producers ────→  [ KAFKA CORE ]  ────→ Consumers
                    │    (брокеры,     ────→ Kafka Streams ── обработка на лету
                    │     топики,       ────→ Schema Registry ── схемы данных (Avro/Protobuf)
                    │     партиции)     ────→ ksqlDB ── SQL-запросы к потокам
                    │
                    └─ Admin Client ──── управление кластером
```

- **Kafka Connect** — фреймворк для интеграции с внешними системами. Source-коннекторы читают из БД и пишут в Kafka, sink-коннекторы — наоборот. Сотни готовых коннекторов.
- **Kafka Streams** — Java-библиотека для потоковой обработки. Фильтры, map, агрегации, join, оконные операции. Работает внутри твоего приложения, без отдельного кластера.
- **Schema Registry** — хранилище схем данных (Apache Avro, Protobuf, JSON Schema). Гарантирует, что producer и consumer говорят на одном языке.
- **ksqlDB** — позволяет писать SQL-запросы к стримам и таблицам в Kafka.

## 10. Практический минимум: как попробовать Kafka за 5 минут

Если хочешь пощупать Kafka руками, вот минимальный сетап через Docker Compose:

```bash
# Сохрани как docker-compose.yml и запусти: docker compose up -d
version: '3'
services:
  kafka:
    image: apache/kafka:4.2.0
    ports:
      - "9092:9092"
    environment:
      # KRaft-режим — без ZooKeeper, современный подход
      KAFKA_NODE_ID: 1
      KAFKA_LISTENERS: 'PLAINTEXT://:9092,CONTROLLER://:9093'
      KAFKA_ADVERTISED_LISTENERS: 'PLAINTEXT://localhost:9092'
      KAFKA_CONTROLLER_LISTENER_NAMES: 'CONTROLLER'
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: 'CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT'
      KAFKA_PROCESS_ROLES: 'broker,controller'
      KAFKA_CONTROLLER_QUORUM_VOTERS: '1@localhost:9093'
    volumes:
      - kafka-data:/var/lib/kafka/data

volumes:
  kafka-data:
```

После запуска можно создать топик, отправить и прочитать сообщение:

```bash
# Создать топик "hello-world"
docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --create --topic hello-world \
  --bootstrap-server localhost:9092

# Отправить сообщение
echo "Привет, Kafka!" | docker exec -i kafka \
  /opt/kafka/bin/kafka-console-producer.sh \
  --topic hello-world --bootstrap-server localhost:9092

# Прочитать сообщения (с самого начала)
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --topic hello-world --from-beginning \
  --bootstrap-server localhost:9092
```

## Резюме

| Вопрос | Ответ |
|--------|-------|
| **Что такое Kafka одной фразой?** | Распределённая платформа для публикации, хранения, обработки и replay потоков событий |
| **Ключевое отличие от очередей?** | Сообщения не удаляются после чтения — это постоянный лог событий, доступный для перечитывания |
| **Когда использовать?** | Высокий объём + много consumers + нужна история + нужна надёжность |
| **Когда НЕ использовать?** | Низкий объём, два сервиса, fire-and-forget, batch ETL, request-reply |
| **С чего начать?** | `docker compose up` с образом `apache/kafka`, создать топик, написать и прочитать сообщение |
